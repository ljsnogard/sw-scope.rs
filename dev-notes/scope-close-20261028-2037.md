# Scope::close、移除 ScopeHeader 与链表集成测试

- 分支：`feat/root-strongchunk`
- 日期：`2026-10-28 20:37`
- 状态：**52 个库测试 + 3 个集成测试通过**

## 1. 移除 ScopeHeader

`Scope` 不再指向单独的 `ScopeHeader`，而是像一个 `Sharing` 一样直接持有域实体的
`NonNull<StrongChunkBase>`：

```text
Scope { chunk_: NonNull<StrongChunkBase> }

StrongChunk<ScopeEntity<A>>
└── data: ScopeEntity<A> {
        lock_: ScopeLock,   // 内含 ScopeInner
        alloc_: A,
    }
```

- `ScopeEntity` 没有额外头部；`lock_` 是首字段，所以 `chunk.data_addr_()` 就是
  `ScopeLock` 地址。
- `Scope` 从 chunk 数据地址取得锁，从锁的 `as_mut_ptr()` 取得 `ScopeInner`；不需要知道
  具体 `A`，因为 `ScopeInner.allocator_` 已经指向实体尾部的分配器。
- 句柄计数、`closed`、`close_requested` 放到 `ScopeInner` 的原子字段里；这些字段只在
  `Scope::clone` / `Drop` / `close` 的锁外路径访问。
- `ScopeInner.lock_` 是回到包含自身之锁的自指指针，供弱槽位 → 域的延迟清盘重试使用；
  它不是 `RootScope` 指针，实体 / 弱池 / `Scope` 都不保存 root。
- `ScopeHeader` 类型与 `ScopeHeader::root_` 等字段已删除。

## 2. Scope::close 的安全语义

`Scope::Drop` 仍然只做关闭标记，不主动清盘；显式新增：

```rust
pub fn close(self)
```

它标记本域关闭并立即尝试清盘：

1. 取本域写锁（`try_write`，析构路径不阻塞）；
2. 遍历所有槽位：`Created`（仅由 `Retain` 持有）的对象立即强制析构；
3. `Owning` / `Sharing` 指向的对象跳过并保留；`Destroying` 也跳过；
4. 级联析构中已经被别的路径处理的槽位由 `try_claim_destroy` 判为已处理；
5. 只有所有槽位都不再存活（没有视图残留）时，才整链回收强池，并把每个槽位的
   `strong_chunk_` 置空；
6. 视图释放、最后一个 `Retain` 释放、或句柄析构时都会重试。

`Owning` / `Sharing` 释放时（以及最后一个 `Retain` 释放时）会通过
`try_flush_for_slot_` 重试一次，因此视图本身不会在存活期间被误析构；但视图之外的
`Created` 对象会在 `close` 当场清除。

外部 `Retain` 不需要等待：指向已清除对象的 `Retain` 只是失效句柄，`try_owning` /
`try_sharing` 返回 `None`，不会解引用已回收的数据。弱池与槽位内存保留，因为跨 Scope
的 `Retain` 仍可能指向它们；强池在全部槽位死亡后才回收。

## 3. 为什么只保留视图目标

- `Retain` 本身只是身份句柄，没有直接数据指针；它只能通过 `try_owning` /
  `try_sharing` 取得视图，而这两个操作会先检查状态。
- `Owning` / `Sharing` 持有的是直接数据视图；在它们存活时强制析构会让借用悬空，所以
  视图指向的槽位必须跳过。
- 视图指向的节点可能还持有其他 `Retain`；这些 `Retain` 的目标如果没有直接视图，就属于
  “仅由 Retain 持有”，在 `close` 时应当被清除。之后这些 `Retain` 自然变成失效句柄。
  这正是 `Retain` 的预期语义：它保证“目标还活着时能升级”，不保证目标永远活着。
- 因此策略是**逐对象**决定：跳过 `Owning` / `Sharing` 目标，清掉其余 `Created`。
- 如果视图被 `mem::forget`，只会保留它直接指向的槽位及其强池；不会被永久推迟整域。

## 4. 链表集成测试

删除了旧的 `tests/pre_drop_.rs`、`tests/scope_api_.rs`、`tests/scope_lifecycle_.rs`
（它们依赖已经移除的同步 API / 父子域）。

新增 `tests/linked_list_.rs`：

1. **同域循环链表**
   - 6 个节点用 `Retain<Node>` 连成双向环；
   - 删除中间节点：改邻居链接 + 释放唯一外部句柄，断言该节点 `Drop` 立即执行；
   - 更新一个节点并遍历校验；
   - 释放 head，仅剩环；断言计数不变；
   - `Scope::close` 后断言所有剩余节点各析构一次。

2. **跨域循环链表**
   - 3 个 Scope，6 个节点轮流放入不同 Scope，再连成跨域双向环；
   - 同样删除节点、更新、释放所有外部句柄；
   - 依次 `Scope::close`，断言所有节点（含此前删除节点）最终各析构一次。

3. **Owning / Sharing 存活时 close**
   - 5 节点循环链表，对节点 1 取 `Owning`、节点 3 取 `Sharing` 并克隆；
   - 释放其余外部句柄后 `Scope::close`；
   - 仅由 `Retain` 持有的节点 0/2/4 立即析构；节点 1/3 保留，视图仍可读取；
   - 视图持有的 `Retain` 指向已清除目标时，`try_owning` / `try_sharing` 返回 `None`；
   - 释放 Sharing 克隆；释放 Owning 后节点 1 被清除；释放最后一个 Sharing 后节点 3
     被清除，5 个节点各析构一次；之后释放失效外部 `Retain` 不会重复析构。

“内存当场释放”在本设计中由**析构立即执行**证明；`StrongPool` 仍是 bump-only，
不会逐块把单节点内存还给 OS。测试因此断言的是 `Drop` 次数与顺序，而不是分配器计数。

## 5. 仍未决

1. 弱池 / 域实体内存仍不可逐域归还；`Scope::close` 只回收强池，弱池保留给跨域
   `Retain`。
2. 有 `Owning` / `Sharing` 被泄漏时，整域数据会保留（安全泄漏）。
3. `StrongPool` 没有单块空闲链，单个对象删除不会归还其强块内存。
4. `ScopeInner` 的原子字段内联在锁里、锁外访问；后续若做更严格的别名审计，可考虑
   单独的状态字/缓存行，但不再恢复 `ScopeHeader`。
5. `Scope::collect` 不再存在；显式生命周期边界统一为 `Scope::close`。
