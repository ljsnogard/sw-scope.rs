# StrongChunk 存活链与销毁状态机

- 日期：2026-09-21 19:35
- 模块：`strong_` / `scope_inner_`
- 状态：设计已定，实现待办

## 1. 背景与需求

SW-scope 本质是 Arena：用户数据可能短期内不断增长，其中大多数在短暂使用后，要么经由
`Owning` / `Sharing` 智能指针被申请释放，要么留在 `StrongChunk` 中，等 Scope 清盘时
一次性收回。因此 `StrongChunk` 必须能分辨两件事：

1. 哪些块在清盘时还需要主动运行 `Drop`，哪些已经被智能指针 Drop 时连带释放掉了；
2. 这些块分布在多个 `ChainedPool` 上，清盘时必须能找到全部存活块，且不能重复 Drop。

## 2. 现有设计盘点

已经具备的部件：

| 部件 | 位置 | 作用 |
| --- | --- | --- |
| `DataState`（3 bit） | `weak_/chunk_.rs` | `Reclaimed / Created / Owning / Sharing / Destroyed`，即"该不该 Drop"的位图 |
| `WeakChunk.strong_chunk_` ↔ `StrongChunkBase.weak_chunk_` | 两处 | 弱槽位与强块互相定位 |
| `StrongChunkState.pool_` | `strong_.rs` | 按 cell 偏移反推所属池 |
| `StrongChunkState.refc_` | `strong_.rs` | `Sharing` 的引用计数 |
| `weak_state_` 的锁位 + `WeakChunkStateGuard` | `weak_/chunk_.rs` | 状态切换的自旋锁 |
| `ChainedPool.used_count_` + 顺序分配 | `scope_inner_.rs` | Arena 的整块兜底回收 |

缺口（按严重程度）：

1. **缺存活链的头**。`ChainedPool.used_count_` 只表示"用到了第几个 cell"，分不清该位置是
   在用块还是已 Drop 的空壳；仅靠扫描 `0..used_count_` 反推槽位边界会算错。
   `StrongChunkState.prev_` 本是为串链预留的，但 `ScopeInner` 没有指向强块链的字段。
2. **缺 `cell_len_`**。`ChainedPool` 是纯 bump 分配，用户的 `T` 大小任意，一个强块占任意
   多个 cell。没有长度就无法算下一个 chunk 的地址（跨池链更是如此）。
3. **缺"恰好销毁一次"的统一裁决点**。数据可能被三条路径销毁：`Owning::drop`、
   `Sharing::drop` 把计数减到 0、清盘兜底；并发或级联时会重复 Drop。
4. **`is_data_alive` 语义待写死**（现已确认，见 §5）。
5. **空间空洞不做复用**（现已确认，见 §6）。

## 3. 存活链归属：ScopeInner，而不是 ChainedPool

**结论：存活链属于 `ScopeInner`，`ChainedPool` 只是内存管理单位。**

依据：

- `ChainedPool` 的机制只解决"分块申请与管理内存"，是内存布局单位。而**存活链表达的是所有权
  关系**——哪个 `StrongChunk` 里还放着可能需要 Drop 的数据。数据之间的循环引用链、依赖链
  由用户的数据结构决定，完全可以横跨多个 `ChainedPool`；对象在池 A，它引用的对象在池 B，
  是常态而非例外。
- 所以池内不能承载一条"恰好覆盖本 Scope 全部存活对象"的链。更关键的一致性理由是：**跨池
  引用意味着池不能单独释放**。若允许"某个池里全部存活块都销毁了就把该池整块回收"，那么
  别的池里指向它的引用立刻悬空。Arena 的整块回收只能发生在**整个 Scope 静默时一次完成**，
  存活链自然也就只能是 Scope 级的。
- 由此定下：`ChainedPool` 保持"内存管理单位"的定位（只负责 bump 分配与整块回收），
  `ScopeInner` 持有链头/链尾，是存活信息的唯一权威来源。池内不再保留任何存活位图，
  避免两处状态互相打架。

`ScopeInner` 需要新增（在既有 `chain_head_` / `chain_tail_` 指向池链之外）：

- `live_head_`: `Option<NonNull<StrongChunkBase>>`
- `live_tail_`: `Option<NonNull<StrongChunkBase>>`

## 4. StrongChunk 的字段与布局

### 4.1 删除 `pool_`

原注释称 `pool_` 是"ChainedPool 内存池距离此地址有多少个 cell"，它其实是该 chunk 在**自己
那个池内**的 cell 下标，只对定位自己的池有意义。既然存活链已经改用跨池的完整指针，`pool_`
的用途只剩"由 chunk 反查所属池"，而 `prev_`（若保留为池内偏移）本就隐含了池身份。

**结论：删除 `pool_`。** 由 chunk 反查所属池的需求，等 Scope 清盘或回收路径真正需要时，
再用"chunk 地址与池基址比对"或新建的池记录来满足，不要为此保留一个自相矛盾的 16 位偏移。

### 4.2 链接字段与状态分离

存活链的链接字段（两个指针）**必须放在 chunk 的最前面**，让"chunk 地址"与"链接地址"有固定
关系；状态字段放在其后。因此把 `StrongChunkState` 中与链相关的内容拆出去，`StrongChunkBase`
的结构改为：

```text
偏移 0   next_live_ : AtomicPtr<StrongChunkBase>
偏移 8   prev_live_ : AtomicPtr<StrongChunkBase>
偏移 16  state_     : AtomicU64/AtomicU32（DataState + 引用计数等）
偏移 24  weak_chunk_: NonNull<WeakChunk<()>>
```

按 64 位平台计算：`StrongChunkBase` = 32 字节，天然 8 字节对齐，无填充；`StrongChunk<T>`
的头部因 `#[repr(C)]` 与首字段对齐一致，`data_` 的偏移仍是 8 的倍数。**这满足"StrongChunk
必须内存对齐"的要求**。

要保留/新增的状态字段：

- 删除 `pool_: PoolIndex`；
- `prev_: PoolIndex` 不再是"距上一个 StrongChunk 多少个 cell"，改由 `prev_live_` 指针表达；
- 新增 `cell_len_: PoolIndex`（u16），记录本块（含头部与数据）占用的 cell 数。容量上界
  `65535 * CELL_SIZE`，默认 CELL_SIZE=8 时为 512 KB，超过则分配失败——需要在上层明确报错；
- 保留 `refc_: Atomic<u32>`。

### 4.3 文档要求

`StrongChunk` 的说明文档必须写清两件事：

1. **存活链机制**：谁在什么时候把块挂上链/摘下链；链的职责是"记录所有数据尚未被 Drop 的
   块"，早期销毁会即时摘链，Scope 静默时链应已为空；整块回收只在静默时发生。
2. **为什么某些 chunk 被 Drop 之后存活链依然有效**：摘链与 Drop 的先后次序、节点被从链中间
   摘除时如何修补前后指针，以及"摘链"与"销毁"各自的成立条件。不能假设链操作与用户
   `Drop` 的执行发生在同一线程。

## 5. `is_data_alive` 的语义（已确认）

`is_data_alive` 为真当且仅当 `DataState ∈ {Created, Owning, Sharing}`，即"数据尚未被销毁"，
**不是**"还存在强引用"。只剩 `Retain` 的块（弱计数 ≥ 1、无强引用）依然 alive，
`try_owning` / `try_sharing` 才是可用的。

## 6. 空间复用（已确认）

不做内存空洞复用。`Owning` / `Sharing` 的"申请释放"只兑现为**析构函数按引用计数及时执行**，
空间本身要等整块清盘才复用。策略是"少量、频繁地清盘"，以整块复用代替小块复用，
不为寻找零散可复用空间付出代价。

## 7. DataState 状态机

### 7.1 状态划分

现有 5 态保留并补充 `destroy` 语义（值可调整，3 bit 有余量）：

| 状态 | 含义 |
| --- | --- |
| `Reclaimed` | 未使用/已可复用，弱槽位空闲 |
| `Created` | 已分配，仅被 `Retain` 持有 |
| `Owning` | 被 `Owning` 独占持有 |
| `Sharing` | 被 `Sharing` 共享持有 |
| `Destroying` | **已认领销毁，但数据 Drop 尚未完成**（新增） |
| `Destroyed` | 数据已 Drop，内存待清盘回收 |
| `Finalized` | 强块已退出存活链，可随 Scope 一并回收（新增，作为"已纳入 GC 队列"的终态） |

关键补充说明：**待清理队列不落在 chunk 的状态位里**，而由"存活链 + 每块的状态"共同表达。
存活链本身就是清盘队列的实体。状态位只负责"这块钱当前归谁、销毁到哪一步"，
避免"队列态"与"生命周期态"两个维度挤在一个字段里。

### 7.2 状态转换的前提与触发行动

| 起点 | 终点 | 前提 | 触发者与行动 |
| --- | --- | --- | --- |
| `Reclaimed` | `Created` | 弱槽位已分配且初始化完毕 | `Scope::try_put` 系列：写数据、挂链、置 `Created` |
| `Created` | `Owning` | 该块无强引用持有者 | `Retain::try_owning`（持锁 CAS） |
| `Created` | `Sharing` | 同上 | `Retain::try_sharing`：置状态并把 `refc_` 置 1 |
| `Owning` | `Destroying` | `Owning` 独占，无并发持有者 | `Owning::drop`：认领销毁后运行 `T::drop` |
| `Sharing` | `Destroying` | `refc_` 减到 0 | `Sharing::drop`：最后一次减计数成功者认领销毁 |
| `Sharing` | `Sharing` | `refc_ > 0` | `Sharing::clone` / `drop`：仅增减计数 |
| `Owning`/`Sharing`/`Created` | `Destroying` | 无强引用，或引用计数已达 0 | **Scope 清盘 sweep 兜底认领** |
| `Destroying` | `Destroyed` | 已认领且 `T::drop` 执行完毕 | 认领者：置 `Destroyed`，**是否同时摘链见 §7.3** |
| `Destroyed` | `Finalized` | 强块已退出存活链，弱引用计数为 0 | 清盘收尾：置 `Finalized`，随池整块回收 |

`try_claim_destroy` 的判据（唯一裁决点）建议为：以原子 CAS 把状态从
`{Created, Owning, Sharing}` 之一搬到 `Destroying` 即成功；若读到的已经是
`Destroying` / `Destroyed` / `Finalized` / `Reclaimed`，则直接失败。升级路径
（`try_owning` / `try_sharing`）只在 `Created` 上成立，因此数据一旦进入销毁流程，
弱引用侧的升级会自然失败，不需要额外的"销毁中"检查。

不变量：

1. **认领唯一**：任何块从"可销毁"进入 `Destroying` 只允许一次，由一次原子 CAS 决定，失败者
   不得再 Drop 数据。
2. **摘链与销毁解耦**：sweep 只会 `try_claim_destroy`，认领失败说明别的线程已处理，跳过即可。
3. **并发安全**：`Sharing::drop` 可能发生在任意线程，而清盘也只保证"同一时刻只有一个 `Scope`
   能操纵 `ScopeInner`"。因此链的增删必须用原子指针完成，且**不能假设 ChainedPool 只被
   单线程访问**。具体取舍见 §7.3。
4. `Created` 状态的大前提是"无强引用"，`Owning`/`Sharing` 的升级都必须先通过弱状态锁
   （`WeakChunkStateGuard`）。

### 7.3 摘链时机：惰性摘链 vs 即时摘链

"存活链"这个名字容易被误读。它承载的是**清盘时的待处理名单**，而不是"每一刻都恰好等于
当前存活集合"的精确集合。两种做法各有取舍，需要择一：

**方案 A：惰性摘链（建议）**

- 数据被销毁（`Destroying` → `Destroyed`）时**不动链**，节点留在链上成为"墓碑"。
- 只有 Scope 清盘 sweep 在单线程静默期才真正把节点摘除、置 `Finalized`。
- 并发的链操作因此只剩一种：新块**原子地挂到链尾**（追加）。`Sharing::drop` 造成的销毁
  完全不需要碰链，也就没有"从链中间摘除"这类最难做对的并发操作。
- 清盘时要求：sweep 只处理认领成功的块；墓碑节点只做摘链，不重复 Drop。
- 代价：链上节点数等于该 Scope 曾分配过的强块总数（直到清盘），而不是当前存活数。对一个
  本来就以整块清盘为兜底的 Arena 来说，这个代价可以接受。

**方案 B：即时摘链**

- 数据一被销毁就立刻把节点从链中间摘掉，链始终只含真正"数据未 Drop"的块。
- 代价：需要双链表 + 认领 CAS 共同保证并发摘链的正确性（前驱/后继的原子修补、以及
  与并发 sweep 的竞争）；复杂度显著高于方案 A。

**方案 A 恰好正面回答"为什么某些 chunk 被 Drop 之后存活链依然有效"**：因为销毁只改状态位、
不碰链接；链的结构完整性与数据的销毁进度互不干涉。这也是把它列为建议方案的主要原因。

两种方案下 `T::drop` 的执行顺序约束都一样：先认领（CAS 成功），再 Drop 数据；数据 Drop
期间可能级联触发别的块的认领与销毁，但只要每块各自遵守"认领唯一"，级联就不会重复处理。


## 8. 循环引用检测：本阶段不做（已确认）

理由：

1. 循环的唯一来源是 `Sharing` 互相持有；`Owning` 独占、`Retain` 只是句柄，都不构成所有权环。
2. 无环数据的正确性完全由引用计数保证，不需要 sweep。
3. **不可达的环不会导致清盘漏 Drop**：环内计数互相撑着，计数路径不销毁它们；但清盘的
   存活链扫描按状态位兜底，会把环内每块各销毁一次。差别只是回收时机推迟到清盘，而本
   Arena 本就以清盘为兜底，这是设计预期。
4. 真正的 trial deletion 需要额外的标记色、待定列表和试删期竞态处理，代价与收益不成比例，
   而且 §6 决定不做空间复用，提前回收内存这件事本身也没有额外收益。

**注意区分**：待清理列表是必须的，但它与循环检测无关。级联析构（某块 Drop 内又释放另一个
`Sharing`，计数归零再次触发销毁）会把重入引入清盘路径，必须靠"认领 CAS + 存活链"把销毁
动作线性化，否则会破坏池的 `used_count_` / 空闲链不变量。

## 10. 实现记录（2026-09-21）

本轮已落地 `src/strong_.rs` 的骨架与 `src/scope_inner_.rs` 的链头/清盘：

- **头部布局**：`StrongChunkBase` = `{next_live_, prev_live_, state_, weak_chunk_, drop_}`，
  64 位平台上 48 字节、8 字节对齐、无填充；`StrongChunk<T>` 的数据区因此始终从 8 的倍数偏移。
- **状态字**：`StrongChunkState` 把状态位（高 4 位）与 `Sharing` 计数（低 28 位）放进同一个
  `AtomicU32`，避免两个维度分别读写而撕裂；`Created` 同时充当"无强引用"的判据与上锁动作。
- **类型擦除析构**：清盘只拿得到 `StrongChunkBase`，因此头部随块登记
  `{drop_fn, data_ptr}`，由 `drop_data_in_place` 调用单态化入口。
  `?Sized` 数据需要额外保存虚表元数据才能重建胖指针，本 crate 的切片走
  `[MaybeUninit<T>]` 数组路线，因此登记入口暂限定 `T: Sized`。
- **`used_count_` 保留**，它是 bump 分配与"是否该开新池"的判断依据（原 `pool_` 已删除）。
