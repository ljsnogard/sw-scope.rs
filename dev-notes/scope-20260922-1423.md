本文记录 2026-09-22 讨论定下的四件事：`ScopeStr` 的形态、`TrEmplace` 的元数据、
`Scope` 的代际结构，以及**清盘方案 A**（含 A/B/C 的取舍理由与清盘顺序）。

## 1. `ScopeStr` 定为 DST

```rust
#[repr(transparent)]
pub struct ScopeStr(str);
```

**理由（决定性）**：用户要求 `ScopeStr` "直接能当 `String`（`str`）来用"。只有把它做成
`str` 的透明 DST 才能满足：

- `Retain<ScopeStr>` 的 `?Sized` 元数据就是长度，`&*retain` 直接是 `&str`；
- `Deref<Target = str>` / `Borrow<str>` 都是零成本转发。

被否决的备选（用 `Retain<[u8]>` 存字节、`ScopeStr` 退化成视图）：那样 `ScopeStr` 是 **Sized
包装**，`Retain<ScopeStr>` 会变成"指向包装的句柄"，既不 unsized、也拿不到直接的 `&str`，
达不到"当 `str` 用"的效果。

连带：`try_put_str` 会走 `?Sized` 分配路径，落回 D4（`?Sized` 元数据放哪）。槽位的 `meta_`
已经在，长度先存那里即可，**D4 维持"留槽位"**。

**已落地**：`ScopeStr` 已是 `#[repr(transparent)] pub struct ScopeStr(str)`，
`Deref`/`Borrow<str>`/`AsRef<str>`/`Debug`/`Display` 都零成本转发；`try_put_str` 走
`emplace_value_with_`，`meta_` 存的就是长度。

## 2. `TrEmplace` 加关联元数据类型

```rust
pub trait TrEmplace {
    type Target: ?Sized;
    /// 重建 `*mut Target` 所需的元数据（`Sized` 时为 `()`）。
    type Meta: Copy;
    type Result<'f>: core::ops::Try<Output = &'f mut Self::Target> where Self: 'f;

    /// arena 先取元数据、构造好 `*mut Target`，再调用 `emplace` 就地写入。
    fn meta_(&self) -> Self::Meta;

    /// # Safety
    /// - 就地构造的结果必须满足 drop 语义；
    /// - 不得越过 `layout` 划定的范围。
    unsafe fn emplace(self, layout: Layout, place: *mut Self::Target);
}
```

**为什么元数据由 emplace 对象暴露**：原死循环是"要构造 `*mut Target` 得先有元数据，而元数据
本该由这次 `emplace` 调用给出"。把 `meta_()` 提到 arena 调用 `emplace` 之前，arena 就能先建
胖指针、再交回给 `emplace`，循环解开。

`IntoEmplace<F, T>` 相应多收一个元数据：`new(factory, meta)`，`Meta = T::Metadata`；
`Sized` 传 `()`。

**实现时的补充（已落地）**：关联类型必须收紧成

```rust
type Meta: Copy + Into<<Self::Target as core::ptr::Pointee>::Metadata>;
```

因为 arena 必须把元数据**存进弱槽位**、日后按 `Target::Metadata` 重建胖指针；取
`Target::Metadata` 时走自反的 `Into` 即可。`IntoEmplace` 因此取 `type Meta = T::Metadata`。

**已落地验证**：`try_put_str`、`try_emplace`（`Sized` 与 `[u64]` 两种目标）、
`try_emplace_with` 的集成测试见 `tests/scope_api_.rs`（5 个用例全绿）。

## 3. `Scope` 的代际结构

`parent_scope_` 已有，按讨论再加四个（都在 `ScopeInner`，均为 `Option<NonNull<ScopeInner>>`）：

```text
prev_sibling_ / next_sibling_   // 同一父下的兄弟双向链
first_child_  / last_child_     // 自己派生的子双向链
```

- `last_child_` 让 `child_scope()` **O(1) 追加**；
- `prev_sibling_` 让"摘下尾子节点"**O(1)**，正是第 4 节"弟先兄后"遍历需要的；
- `next_sibling_` 供独立 drop 中间子 Scope 时摘链。

`children_num_` 删除：它原本只被"子 scope 数"用，而 `last_child_.is_none()` 就是"没有子域"，
正好是 D1b 要的静默判据。该字段改为 `flags_: AtomicUsize` 保存标记（见 §6.4）。

## 4. 清盘顺序与非递归遍历

顺序（已定）：**子先父后、弟先兄后**（后加入的 Scope 先清盘）。

后序、弟先兄后、**O(1) 栈**的遍历：从 `last_child_` 一路下潜到叶子，摘掉"尾子节点"，
再决定是回父还是继续下潜下一个尾子树：

```text
cur = 子树根
loop {
    while let Some(c) = cur.last_child_ { cur = c; }      // 下潜到最"幼"的叶子
    match cur.parent_scope_ {
        None => { close_scope(cur); break; }              // 到子树根
        Some(p) => {
            p.last_child_ = cur.prev_sibling_;            // 摘掉尾子节点（O(1)）
            if let Some(pr) = cur.prev_sibling_ { pr.next_sibling_ = None; }
            if p.first_child_ == Some(cur) { p.first_child_ = None; }
            close_scope(cur);
            cur = match p.last_child_ { Some(c) => c, None => p };
        }
    }
}
```

不变式：**总是从 `last_child_` 下潜、只摘尾子节点**，因此每一步 `cur` 都是某个父的尾子节点，
摘完尾后 `p.last_child_` 自然指向"次幼"的兄弟。整趟 O(节点数)、O(1) 栈，不递归。

## 5. 三条清盘路线 A/B/C，以及为什么选 A

问题背景：`Retain<T>` 是**刻意不带生命周期**的 GC Handle，`child_scope(&self) -> Scope` 也返回
无生命周期的 owned 句柄，因此它们都可能比所属 `Scope` 活得久：

```rust
let parent = Scope::new();
let child  = parent.child_scope();
drop(parent);          // 若此刻真去释放，child 的 ScopeInner 已无效
let r = child.put(1);  // 悬空

let scope = Scope::new();
let r = scope.put(42);
drop(scope);            // 若此刻真去释放，r 悬空
let x = r.try_owning(); // 悬空
```

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **A（采用）** | `Drop` 只把整棵子树**标记关闭并摘链**；每个 scope 在自己的对象全部销毁、且没有子域时**静默**，静默后（可能是很久以后）才真正回收 | 语义是"drop 触发关闭、静默后回收"；需要一个"待回收"名单与静默判据 |
| B | 给 `Retain` / 子 `Scope` 加生命周期或品牌，使其不可能活过所属 `Scope`，于是 drop 可以安全地立即释放 | 改动核心 API（`Retain<'a, T>`），与"句柄传到哪生命周期带到哪"的初衷冲突 |
| C | 强制清盘，并把"调用时不得有存活句柄"写成 `unsafe` 契约 | `Drop` 不能是 `unsafe`，只能另开 `unsafe fn close()`，等于放弃"drop 即清盘"这条需求 |

**选 A 的原因**：

1. 只有 A 能在保持 `Drop` **safe** 的前提下满足"drop 触发整棵子树清盘"；
2. A 与 README 的原始约定一致——"当其分配的所有 `Retain` 都不再存活，且其所有子 Scope 也不
   存活，这个 Scope 的内存才会被回收"；
3. **关键澄清**：清盘（=把对象 `PreDrop` + 析构、回收池）本来就**不必发生在 `Drop` 调用期间**。
   `Drop` 只负责"标记 + 摘链 + 触发一次静默检查"，真正的回收发生在静默之后——这正是 A。

## 6. A 的落地机制

### 6.1 关闭与展平（`Scope::drop`）

按 §4 的顺序遍历整棵子树，对每个 scope：

1. 置位 `flags_` 的 `CLOSED`；
2. 从父的子链上摘除（同时维护 `first_child_` / `last_child_`）；
3. 把它挂进**整棵树共享的待回收名单**（root 上的 `pending_head_` + 每个 scope 的
   `pending_next_`）。

展平（子节点也各自入名单）之后，每个 scope 都是独立可回收的：它的对象只属于它自己，回收
不需要看别的 scope。

### 6.2 静默判据

一个已关闭的 scope 可回收，当且仅当：

- 它的存活链上**没有任何仍然活着的数据**（逐槽 `DataState::is_data_alive()` 为假），且
- 它没有子域（`last_child_.is_none()`）。

### 6.3 回收触发（先做惰性扫描）

- `reclaim_pending_()`：遍历待回收名单，对静默者执行 `flush_`（`PreDrop` 兜底、归还弱槽位、
  回收强池）并释放 `ScopeInner` 自身内存（`allocator_.deallocate`，注意**不动**共享的
  `weak_pool_` 与 `pre_drop_registry_`）；
- 触发点：**每次 `put` 之前**与 **`Scope::collect`**。不做逐次 `Retain::drop` 的即时回收，
  以免为此在每个弱槽位里多存一个"所属 Scope"指针（那会把 Batch B 省下的 8 字节又加回去）。
- 备选（若日后需要"最后一个句柄消失即回收"）：在弱槽位或 `StrongChunkBase` 里存
  `owner_scope_`，维护每个 scope 的存活对象计数，做到 O(1) 即时回收，代价是每对象 +8 字节。

### 6.4 `flags_` 与"关闭后仍放入"的行为

`children_num_` 改为 `flags_: AtomicUsize`，位定义：

```text
bit 0  CLOSED   该 Scope（及其子树）已被标记清盘
其余位保留
```

关闭后仍调用 `put` / `try_put_with` / `try_emplace*` / `try_put_str` 时：

- **默认**：忽略 `CLOSED`，照常放入（行为与今天一致）；
- 开启 Cargo feature **`strict-put-after-close`** 时：返回 `Err(ScopeError::ClosedScope)`。

即由使用者选择"报错"还是"忽略标记继续用"。

## 7. 实现记录（2026-09-22）

| 项 | 落点 |
| --- | --- |
| `ScopeInner` 代际字段 | `prev_sibling_` / `next_sibling_` / `first_child_` / `last_child_`；`children_num_` 已删除，改为 `flags_: AtomicUsize`（`FLAG_CLOSED` / `FLAG_HANDLE_DROPPED`） |
| 待回收名单 | root 上的 `pending_head_` / `pending_tail_` + 每个域的 `pending_next_` |
| 非递归关闭 | `ScopeInner::close_subtree_`：从 `last_child_` 下潜、摘尾子节点、逐个入名单（子先父后、弟先兄后） |
| 静默与回收 | `is_quiescent_` / `is_reclaimable_` / `reclaim_pending_` / `destroy_scope_`；触发点在"每次 `put` 之前"与 `Scope::collect` |
| `Scope::drop` | 打 `HANDLE_DROPPED` 标记 → 未关闭则 `close_subtree_` → `reclaim_pending_`；**不强制析构**，`Drop` 保持 safe |
| 关闭后放入 | `Scope::ensure_open_`；默认忽略，开启 `strict-put-after-close` 时返回 `ScopeError::ClosedScope` |

**一处实现补充（A 的句柄维度）**：A 只推迟"有存活对象"的回收，但一个**没有对象**的域在关闭后
立刻静默——如果此时还有指向它的 `Scope` 句柄，回收就会让句柄悬空。因此回收判据加上
`FLAG_HANDLE_DROPPED`：只有"**句柄已析构 + 已关闭 + 静默**"才真正释放。这样
`let child = parent.child_scope(); drop(parent);` 之后 `child` 依然有效（测试
`closing_scopes_keeps_live_retain_usable` 覆盖）。

**测试**（`tests/scope_lifecycle_.rs`，默认与 `--features strict-put-after-close` 两种构建都过）：

- `closing_scopes_keeps_live_retain_usable`：A 的核心语义；
- `deep_scope_chain_closes_iteratively`：10 万层子域链，析构顶层句柄不爆栈（递归写法必爆）；
- `put_after_close_is_ignored_by_default` / `put_after_close_errors_under_strict_feature`：feature 两种行为。
