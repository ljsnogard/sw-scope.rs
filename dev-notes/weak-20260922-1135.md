## 1. 本轮要解决的三件事

1. **按类型去重**：`DropVtable` 现在每个弱槽位一份（24 字节），而其中的信息大多与"是第几个
   对象"无关；
2. **新增可选 `PreDrop` 钩子**：用户把数据放进 `Scope` 时（或按类型一次性）注册一个"最后通知"
   函数，在对象**进入清理列表**的那一刻、真正 `drop_in_place` 之前调用；
3. **改名**：`DropVtable` 换成一个不与 `Drop` 混淆、能说明职责的名字（§4.6）。

## 2. 触发时机：进入清理列表（D1 已定）

### 2.1 为什么不能用"最后一个引用释放"作为触发点

`Retain` 是最长寿的句柄，并且**可以互相引用成环**：对象 A 的数据里存着 `Retain<B>`，B 的数据里
存着 `Retain<A>`（或更长的环）。这时环内每个弱槽位的弱计数都被对方撑着，永远不归零，
**"最后一个 `Retain` 被释放"这个事件根本不会发生**。

同一类问题还有：`mem::forget(retain)`、被 `Box::leak` 泄漏的 `Sharing`（见
`strong-20260921-2150.md` §3）。这些都说明：引用计数**不能**作为"该销毁了吗"的判据，
只能作为"还有没有人正在访问"的判据。

因此本轮把触发点明确为：

> **对象被纳入清理列表（cleanup list）的那一刻，就是它被终结的时刻。**

### 2.2 清理列表模型

清理列表的物理载体就是弱槽位上的存活链（`prev_live_` / `next_live_`）。对象进入列表有两种
来源，**两者都属于"被纳入清理列表"，也都在纳入的那一刻跑 `PreDrop`**：

| 来源 | 条件 | 时机 |
| --- | --- | --- |
| (a) 确定性析构 | 计数已经证明不可达：`weak_count == 0 && strong_count == 0` | **立即**，不等清盘 |
| (b) 清盘强制纳入 | Scope 发起清盘时对象仍存活（环、`forget`、泄漏） | 清盘时 |

纳入后依次做三件事：

```text
纳入清理列表
    → 1) 运行 PreDrop 钩子（数据仍然有效，可 &mut）
    → 2) drop_in_place（真正的析构）
    → 3) 标记已销毁；空间随清盘整块回收
```

(a) 就是"及时析构"：`Owning` 析构之后最后一个 `Retain` 紧跟着析构，两个计数同时归零，这一块
**当场**就可以析构，不必等到清盘；`Sharing` 计数归零且 `Retain` 也没了，同理。(b) 是保证
路径：`Retain` 成环时 (a) 永不发生，只有清盘能把它们纳入——这正是
`strong-20260921-2150.md` §3 实证的"唯一在五种普通写法下都不漏的那一支"。

清盘还要能承受级联：把 A 的数据 `drop` 掉会释放 A 持有的 `Retain<B>`，可能当场把 B 推向 (a)。

### 2.3 D1c 已定：确定性析构立即发生

> 更正：本节原先把"是否保留提前析构"写成一个待选项，并把代价写成"被提前析构的对象收不到
> `PreDrop`"。那是错的——`PreDrop` 绑定的是"纳入清理列表"，而确定性析构本身就是纳入来源
> (a)，所以它照样会跑到钩子。原表述已删除。

有些析构是确定性的：`Owning` 析构后最后一个 `Retain` 随即析构、`Sharing` 计数与 `Retain`
同时归零——计数已经证明对象不可达，**当场就可以析构，不必等清盘**。这一条保留。
只有非确定性的（环、`forget`、泄漏）才交给清盘处理。两条来源都跑 `PreDrop`，因此钩子仍是
"每个对象恰好一次"的全量最后通知。

### 2.4 清盘由什么触发（D1b：不属于单个对象的关注点）

清盘有两种可能，设计时**只需假设"清盘会发生"**，不必让每个对象关心它何时发生：

1. **Scope 本身已经没有活着的引用**：子 Scope 数降为 0，且没有强持有对象。
   `ScopeInner` 目前还没有体现这个条件（现在只有 `children_num_`），但它是客观存在的；
2. **显式清盘**：调用方主动调用 `collect()`。

先按"会清盘"设计；把上述静默判据补进 `ScopeInner` 是后续独立的一件事。

### 2.5 与 README 使用思路的关系

README 的示例要求"`Owning` 析构后还能再次 `try_owning`"。这在两条来源下都成立：

- `Owning` / `Sharing` 的析构只**归还访问权**（状态回到 `Created`），不是进入清理列表；
- 此时 `Retain` 还活着（弱计数 > 0），对象不可能被终结。

也就是说，"归还访问权"和"进入清理列表"是两件事；旧笔记把 `Owning::drop`、`Sharing` 计数归零
列为"提前析构路径"，正是把这两件事混为一谈。正确的说法是：它们**不触发**析构，但
"`Owning` 析构 + 最后一个 `Retain` 析构"这个组合会让计数归零，从而走来源 (a) 立即析构。

### 2.6 一条必须写进文档的不变量

> 清盘路径**必须**能在对象仍有外部句柄（环内互持、泄漏、`forget`）的情况下完成
> `PreDrop` + 析构 + 回收；不能假设"进入清盘时引用计数已归零"。

## 3. 现状盘点：`DropVtable` 里到底哪些是类型常量

```text
DropVtable（每槽 24 字节）
    drop_fn_ : Option<unsafe fn(*mut u8, *const ())>   单态化析构入口
    data_    : *mut u8                                  数据区起址
    meta_    : *const ()                                ?Sized 元数据（切片长度 / 虚表）
```

| 字段 | 是什么 | 是否逐对象 |
| --- | --- | --- |
| `drop_fn_` | `drop_in_place::<T>` 的类型擦除入口 | **类型常量**（同一个 `T` 全同） |
| `data_` | 数据区起址 | 逐对象，但 = 强块首址 + **类型常量**偏移，**可推导** |
| `meta_` | `?Sized` 元数据 | **逐对象**（切片长度、`dyn` 虚表都随对象变）——但见 §4.5 |

**结论**：真正"每对象一份的重复"只有 `drop_fn_`。但要注意一个反直觉的点：

> **共享 `drop_fn_` 本身并不省槽位字节**——槽位总得放一个指针来指出"用哪一份登记"。
> 槽位能省下的字节来自 `data_`：它不再需要保存，可以从强块首址推导出来。

这条判断决定了 §4.4 的收益必须如实写成"净省 8 字节"，而不是"省下 16 字节"。
共享登记的价值在别处：`PreDrop` 与 `Drop` 的合成只写一份、将来新增逐类型操作不再逐对象付费。

## 4. 方案：`PreDropRecord` 记录

### 4.1 结构

```rust
/// 一份"该类型的对象进入清理列表时怎么处理"的类型级登记：
/// 先跑可选 PreDrop 钩子，再析构数据。
///
/// 每个具体 `T`（以及带对象级钩子时的每个 `(T, Fin)` 组合）只生成一份，提升进静态内存。
/// 弱槽位只保存 `&'static PreDropRecord`，于是逐对象的类型信息被压缩成一个指针。
#[repr(transparent)]
pub(crate) struct PreDropRecord {
    /// 类型擦除的清理入口：接收"强块首址 + `?Sized` 元数据"。
    ///
    /// `None` 表示该类型既不需要 `Drop`、也没有 `PreDrop` 钩子，清理时什么都不做。
    entry_: Option<unsafe fn(*mut u8, *const ())>,
}
```

字段里**没有** `data_`，也**没有** `meta_`：`data_` 由入口自己按 `T` 单态化重建（§4.3）；
`meta_` 是逐对象的，仍留在槽位（§4.4、§4.5）。

### 4.2 怎么做到「每类型一份」：关联常量 + 取引用

不需要类型表，也不需要锁。Rust 的**关联常量 + 取引用**会为每个单态化生成一份 `'static`
内存，这正是 gc-arena 的做法（`CollectVtable` 用 `HasCollectVtable::VTABLE` 物化）：

```rust
impl PreDropRecord {
    /// 无钩子的类型：只有 `needs_drop` 时才有入口。
    pub(crate) fn of<T: ?Sized>() -> &'static PreDropRecord {
        trait HasRecord { const V: PreDropRecord; }
        impl<T: ?Sized> HasRecord for T {
            const V: PreDropRecord = PreDropRecord {
                entry_: if mem::needs_drop::<T>() {
                    Option::Some(drop_entry_::<T> as unsafe fn(*mut u8, *const ()))
                } else {
                    Option::None
                },
            };
        }
        &<T as HasRecord>::V
    }

    /// 对象级：带用户 `PreDrop` 钩子的类型，记录按 `(T, Fin)` 一份。
    pub(crate) fn of_with<T: ?Sized, Fin: FnOnce(&mut T) + 'static>() -> &'static PreDropRecord {
        trait HasRecord<Fin> { const V: PreDropRecord; }
        impl<T: ?Sized, Fin: FnOnce(&mut T) + 'static> HasRecord<Fin> for T {
            const V: PreDropRecord = PreDropRecord {
                entry_: Option::Some(pre_drop_entry_::<T, Fin> as unsafe fn(*mut u8, *const ())),
            };
        }
        &<T as HasRecord<Fin>>::V
    }
}
```

成立的理由：

- `entry_` 只有函数指针，`PreDropRecord` 是 `Sync`，可以 safely 提升为静态内存（**不能**往记录
  里放裸指针，否则 `!Sync`）；
- 每个单态化只对应一份静态内存：同一个 `T`（或同一对 `(T, Fin)`）在任何调用点取到同一个
  `&'static PreDropRecord`，因此**不存在逐对象副本**。本轮已用最小程序验证：同一 `T` 的
  地址相等；
- **注意**：编译器可以合并内容完全相同的常量。例如 `u64` 与 `u32` 都 `!needs_drop`，两者的
  记录都是 `{ entry_: None }`，实测地址会相同。这是允许的，所以**不要拿"记录地址"当类型
  身份用**；本方案也从不依赖地址互不相等；
- 因此**不需要** `TypeId`、哈希、字符串，也不依赖运行期类型信息，`no_std` 下同样可用；
- `!needs_drop::<T>()` 且无钩子时 `entry_` 为 `None`；槽位的 `record_` 本就是
  `Option<&'static PreDropRecord>`，这种类型直接存 `None` 即可。

### 4.3 数据地址怎么来：单态化入口自己重建强块

`StrongChunk<T>` 是 `#[repr(C)] { base_: StrongChunkBase, data_: T }`，`base_` 在偏移 0，
因此"强块首址"与"`StrongChunk<T>` 首址"相同。入口拿着 `T` 就能让编译器算偏移：

```rust
/// 单态化的清理入口：把 `(强块首址, ?Sized 元数据)` 还原成 `StrongChunk<T>` 再析构数据区。
unsafe fn drop_entry_<T: ?Sized>(base: *mut u8, meta: *const ()) {
    let meta = unsafe { raw_to_meta_::<T>(meta) };
    // SAFETY: base 是 StrongChunk<T> 的首地址；meta 来自同一次分配
    let chunk = unsafe { ptr::from_raw_parts_mut::<StrongChunk<T>>(base.cast::<()>(), meta) };
    // SAFETY: 调用方保证数据尚未析构
    unsafe { ptr::drop_in_place(ptr::addr_of_mut!((*chunk).data_)) };
}
```

- `Sized` 时 `meta` 为 `()`；`?Sized` 时是切片长度或虚表，由调用方从槽位的 `meta_` 传入；
- `data_` 与 `data_offset_` 都从记录里消失，"地址是类型常量偏移"这条事实改由编译器在
  单态化里体现，比手写公式更不易错（也顺手覆盖 `?Sized` 的对齐）。

同理，弱槽位上的 `data_ref_as::<U>` 也不再读"存下来的数据地址"，而是用 `strong_chunk_` +
`meta_` 重建 `StrongChunk<U>` 后取 `data_`。

### 4.4 新布局与字节账

```text
WeakChunk<()>（64 位）
    8  chunk_state_
    8  prev_live_
    8  next_live_
    8  strong_chunk_
    8  record_ : Option<&'static PreDropRecord>   ← 取代 drop_fn_
    8  meta_   : *const ()                        ← ?Sized 逐对象元数据（见 §4.5）
    0  PhantomData
```

| 项 | 现状 | 方案 |
| --- | --- | --- |
| `WeakChunk<()>` | 56 | **48** |
| 其中"类型登记" | `DropVtable` 24 | `record_` 8 + `meta_` 8 |
| `StrongChunkBase` | 16 | 16（不变） |
| 每对象合计（弱槽 + 强块头） | 72 | **64** |
| 记录本体 | 每对象 24 | **每类型 8** |

- **净省 8 字节/对象**（56 → 48；约 14%）。来源是删掉逐对象的 `data_`，不是共享 `entry_`。
- 若按 §4.5 的方案进一步消掉槽位里的 `meta_`，可到 40 字节；但该优化依赖 `?Sized` 入口先落地。

### 4.5 `?Sized` 元数据该跟谁（D4 展开，暂不决策）

问题："元数据为什么要跟槽位？为什么不是跟类型，即所有同类型元素共用同一份元数据？"

答案是：**取决于哪一类元数据**。Rust 的 `?Sized` 元数据只有三种，性质完全不同：

| `T` 的形态 | `T::Metadata` | 是否类型常量 | 说明 |
| --- | --- | --- | --- |
| `Sized` | `()` | 是（零字节） | 无需存储 |
| `[E]` 切片 | `usize`（元素个数） | **否** | 两个 `[E]` 对象长度可以不同，天然逐对象 |
| `dyn Trait` | `DynMetadata`（虚表指针） | **取决于怎么建记录** | 见下 |

**切片**：长度逐对象，无法"同类型共用一份"。但它并不是非存在槽位里不可——长度在**分配时就
已知**（`try_clone(&[E])` / `try_alloc_slice_uninit(len)` 都显式拿到元素个数），可以记为强块头
上的一个长度字，需要时推导。位置从弱槽位换到强块头，**每对象总量不变**。

**`dyn Trait`**：虚表指针取决于**具体实现类型**，不取决于被擦除的 `dyn Trait`。也就是说：

- 对固定的具体类型 `C: Trait`，`ptr::metadata(&c as &dyn Trait)` 永远返回同一个静态地址，
  **是类型常量**；
- 前提是登记记录按**具体类型 `C`** 建立，而不是按 `dyn Trait` 建立。放入点正好同时握着 `C`
  （擦除前）与目标 `dyn Trait`，所以这个前提可以满足；
- 于是 `dyn` 的虚表可以放进"每具体类型一份"的记录里，所有 `C` 的对象共用。

**所以对用户问题的直接回答**：

- 对 `dyn Trait`：**可以**同类型共用一份，但"同类型"必须理解为"同一具体实现类型"，且记录要按
  具体类型建立；
- 对切片：**不可以**，长度天生逐对象；但可以让它不占槽位的专用字段，而是从强块的长度记账推导。

**理论上的最优形态**（槽位 40 字节）：

```text
槽位：record_(8)                       // 元数据不再进槽位
记录：meta_of: unsafe fn(*mut u8 /*strong base*/) -> *const ()
      Sized    → 返回 null
      dyn      → 返回该具体类型的虚表常量
      [E]      → 读强块头上的长度字，换算成 usize 元数据
强块头：Sized/dyn 仍 16；切片 24（多一个长度字）
→ 每对象合计：Sized/dyn = 40 + 16 = 56；切片 = 40 + 24 = 64
```

代价与风险：

1. 记录里多一个 `meta_of` 生产者字段（记录从 1 字变 2 字，但仍是**每类型一份**，不影响逐对象）；
2. 强块头要为切片多一个长度字，或想办法塞进现有对齐填充（`StrongChunkBase` 是 16 字节、
   8 对齐，没有现成空隙）；
3. `data_ref_as::<U>` 必须能在不区分 `U` 是哪种 `?Sized` 形状的前提下拿到元数据——靠
   `meta_of` 这个生产者可以做到，但调用链要改成"记录 + 强块"两处取信息。

**我的建议：D4 暂不决策，先保留槽位的 `meta_`。** 理由：

1. `?Sized` 的公开入口（`Scope::try_clone` / `try_alloc_slice_uninit`）目前都是 `todo!()`，
   连一条真实路径都没有；
2. 统一槽位避免了"按元数据种类分支"的复杂度，而现在的复杂度预算应该花在 `PreDrop` 语义上；
3. 收益只有 8 字节/对象（48 → 40），且在 `?Sized` 入口落地前是纯粹的提前优化。
   等切片 / `dyn` 真正跑起来、并有实测说明这个字重要时，再按上面的形态改造。

### 4.6 命名（D3 已定）

| 对象 | 名称 | 理由 |
| --- | --- | --- |
| 用户钩子（trait / 参数） | **`PreDrop`** / `pre_drop` | "最后通知"；真正的 finalize 是 `Drop`，不混用 |
| 每类型一份的登记（原 `DropVtable`） | **`PreDropRecord`** | 与钩子同词根，一眼看出它服务什么 |
| 记录里的合成入口 | `pre_drop_entry_`（先钩子后 `drop_in_place`） | 与 `drop_entry_` 并列 |

备选：`PreDropVtable`（对齐 gc-arena 的 `CollectVtable` 后缀）、`TeardownRecord`、`LastCall`。
倾向 `PreDropRecord`。

## 5. `PreDrop` 钩子 API

### 5.1 两种添加方式与优先级（D2）

优先级只有一条规则：

```text
对象级钩子  >  类型级钩子  >  没有钩子
```

**对象级**（针对特定对象）：放入时随值传入，记录按 `(T, Fin)` 一份，见 §5.3 的
`try_put_with` / `put_with`。

**类型级**（针对该类型在该 Scope 树里的所有实例）：**方案 B，注册表挂在 `RootScope` 上（D2 已定）**。

> **选 B 的初衷**：不能为了 `PreDrop` 强迫使用者给**每个**类型实现一个 trait（例如
> `TrPreDrop`）。注册表本身可以由一个**专门构造的类型**来承载，在运行期装配——用户只对自己
> 关心的类型调用一次 `set_pre_drop::<T>` 即可，其余类型走"无钩子"的默认记录。

```rust
// RootScope 新增字段（与 weak_pools_ 并列，随整棵树回收）
pre_drop_registry_: Option<NonNull<PreDropRegistry>>,

struct PreDropRegistry {
    /// 只登记"被显式注册过的类型"，典型数量很小，线性扫描即可
    entries_: Vec<PreDropEntry>,
}
struct PreDropEntry {
    key_: &'static str,                  // core::any::type_name::<T>()
    record_: &'static PreDropRecord,     // PreDropRecord::of_with::<T, Fin>()
}
```

- **注册**：`scope.set_pre_drop::<T, Fin: FnOnce(&mut T) + 'static>(hook: Fin)`。记录仍是 §4.2 的
  const 提升产物（每 `(T, Fin)` 一份），**表里只存一个 `&'static` 指针**；因为钩子零尺寸，
  运行期不为钩子本身保存任何状态。
- **放入**：`try_put` 时先看有没有对象级钩子；没有就按 `type_name::<T>()` 查表；再没有就用
  `PreDropRecord::of::<T>()`。选中的记录指针写进槽位，槽位仍然只占一个字。
- 表随 `RootScope` 回收，**无全局锁**；同一 `RootScope` 下的子 Scope 共享这张表，正符合
  "针对该类型的所有实例"。
- 只在**注册**与**放入**时触碰，访问 / 析构热路径不受影响。
- `RootScope` 是手工初始化的（`try_init_default_root_scope_`），注册表的初始化要并进那段流程。
- 纯 `core`（关闭 `core-alloc`）时没有 `Vec`：注册表可退化为侵入式链表，或该 feature 下不提供
  类型级钩子。实现时按 feature 处理。

**表键的选择（子决策 D2c，有一个坑必须先说清）**：**不能**拿"每类型一份常量的地址"当 key。
本轮实测发现**内容相同的常量会被编译器合并**（`u64` / `u32` 的 `None` 记录地址相同），地址
一旦合并，不同 `T` 的类型级钩子就会互相串味。可选：

| key | 优点 | 缺点 |
| --- | --- | --- |
| `core::any::type_name::<T>()` | `core` 可用；不要求 `T: 'static`；按完整路径区分 | 文档声明"不保证唯一"（实际不同路径不同）；需字符串比较 |
| `core::any::TypeId::of::<T>()` | 精确 | 要求 `T: 'static`，与"`Retain<T>` 可以带借用"冲突 |
| `(type_name, size_of, align_of)` | 更保守 | 仍以字符串为主键 |

倾向 `type_name`（或第三种组合）。**D2c 暂定 `type_name`，先按它做基础设施，用实验验证；
不行再换（不排除换回"类型常量地址 + 强制内容不合并"的写法）。**

### 5.2 不允许捕获环境、`'static`（D2 已定）

钩子必须是**零尺寸类型**（函数项或非捕获闭包），并显式要求 `'static`（拥有独立生命周期，
不借用外部栈帧）。这样钩子完全由类型决定，能进 §4.2 的常量，**逐对象零额外开销**：

```rust
/// 取出零尺寸钩子的唯一值。
///
/// # Safety
///
/// `Fin` 必须是零尺寸类型。零字节不承载任何位模式，因此"读未初始化内存"得到的仍是该类型
/// 唯一的值。
unsafe fn zst_value_<Fin>() -> Fin {
    const { assert!(mem::size_of::<Fin>() == 0, "PreDrop 钩子必须是非捕获闭包或函数项") };
    // SAFETY: 由 const 断言保证 Fin 为零尺寸
    unsafe { mem::MaybeUninit::<Fin>::uninit().assume_init() }
}
```

捕获式闭包会在**编译期**被上面这条 `const` 断言挡下（报错信息就是那句中文）。

需要点破一处容易误解的地方：`try_put_with(factory, pre_drop)` 会按值收下 `pre_drop`，但
**只把 `Fin` 的类型当作登记键**——真正被调用的是清理那一刻由 `zst_value_::<Fin>()` 现取的
零尺寸值。两者之所以等价，是因为非捕获闭包 / 函数项是零尺寸类型、只有一个值；被收下的那个
值本身是零尺寸，析构即无操作。换言之，钩子不携带任何运行期状态，这正是它能进"每类型一份"
常量的前提。

若日后确实需要捕获环境，唯一不倒退的扩展是把 `Fin` 值存进强块
（`{ base_, pre_drop_: Fin, data_: T }`，记录仍是 `(T, Fin)` 一份），逐对象多付
`size_of::<Fin>()` 字节。本阶段不做。

### 5.3 API 草案（D5：`TrScope` 与 `Scope` 都加）

保持现有 `try_put` / `try_emplace` 不变（不破坏调用方），新增：

```rust
// 对象级钩子：随值传入，只影响这一个对象
pub fn try_put_with<F, T, Fin>(
    &mut self, factory: F, pre_drop: Fin,
) -> Result<Retain<T>, ScopeError>
where F: FnOnce() -> T, Fin: FnOnce(&mut T) + 'static;

pub unsafe fn try_emplace_with<TyEmp, Fin>(
    &mut self, layout: Layout, emplace: TyEmp, pre_drop: Fin,
) -> Result<Retain<TyEmp::Target>, ScopeError>
where TyEmp: TrEmplace, Fin: FnOnce(&mut TyEmp::Target) + 'static;

// 类型级钩子：写进本 Scope 树的 RootScope 注册表，影响该类型的所有实例
pub fn set_pre_drop<T, Fin>(&mut self, pre_drop: Fin) -> Result<(), ScopeError>
where T: ?Sized, Fin: FnOnce(&mut T) + 'static;
```

对应的 panic 版便捷包装 `put_with` / `put_pre_drop`，与现有 `put` 对称。`set_pre_drop` 是
树级配置，建议同时放在 `Scope` 与 `TrScope` 上（D5）。`TrScope` 里逐条加入同名方法
（`TrScope` 目前只有 `&mut Scope` 一个实现，加方法即破坏外部实现——按 D5 已确认接受）。

### 5.4 合成入口与调用时机

```rust
unsafe fn pre_drop_entry_<T: ?Sized, Fin: FnOnce(&mut T) + 'static>(
    base: *mut u8, meta: *const (),
) {
    let meta = unsafe { raw_to_meta_::<T>(meta) };
    let chunk = unsafe { ptr::from_raw_parts_mut::<StrongChunk<T>>(base.cast::<()>(), meta) };
    let data = ptr::addr_of_mut!((*chunk).data_);
    let f = unsafe { zst_value_::<Fin>() };
    f(unsafe { &mut *data });            // 1) 最后通知：数据仍然有效，可 &mut
    unsafe { ptr::drop_in_place(data) }; // 2) 真正的析构
}
```

约定：钩子运行在数据**仍然有效**时，收到 `&mut T`，可取出/释放其中的 `Retain`、`Sharing`
（这正是环被打断的地方）；钩子返回后立即执行正常的 `Drop`。钩子必须把值留在"可析构"的状态。
`!needs_drop::<T>()` 但注册了钩子的类型照样可用：钩子跑完后 `drop_in_place` 是空操作。

调用时机**唯一**：对象进入清理列表、且 `try_claim_destroy` 认领成功之后。登记只回答
"怎么清理"，状态机才回答"该不该清理、由谁清理"：

```rust
pub(crate) unsafe fn run_pre_drop(&self) {
    let Option::Some(record) = self.record_ else { return };
    let Option::Some(entry) = record.entry_ else { return };
    let base = self.strong_chunk_.load(Ordering::Acquire);
    debug_assert!(!base.is_null());
    // SAFETY: 已由 try_claim_destroy 认领，且恰好调用一次
    unsafe { entry(base.cast::<u8>(), self.meta_) };
}
```

## 6. 状态机与引用计数

### 6.1 迁移表（清理列表模型）

| 起点 | 终点 | 触发 | 说明 |
| --- | --- | --- | --- |
| `Created` | `Owning` | `Retain::try_owning` | 无强引用者；CAS 判据唯一 |
| `Owning` | `Created` | `Owning::drop` | 归还访问权，**不是**进入清理列表 |
| `Created` | `Sharing` | `Retain::try_sharing` | 强计数置 1 |
| `Sharing` | `Sharing` | `Sharing::clone` / `drop` | 仅增减强计数 |
| `Sharing` | `Created` | 强计数减到 0 | 归还访问权，**不是**进入清理列表 |
| `Created` | `Destroying` | 计数不可达（弱计数归零且无强引用）— 来源 (a) | 确定性析构，**立即**运行 `PreDrop` |
| `Created` / `Owning` / `Sharing` | `Destroying` | 清盘强制纳入 — 来源 (b) | 环、`forget`、泄漏；保证路径 |
| `Destroying` | `Destroyed` | 认领者执行 `PreDrop` + `drop_in_place` | 恰好一次 |
| `Destroyed` | `Finalized` | 弱计数为 0、退出存活链 | 槽位可回收 |

两条来源共用同一个终态与同一个 `try_claim_destroy` 认领 CAS：来源 (a) 可能发生在任意线程
（`Sharing::drop` / `Retain::drop`），来源 (b) 发生在清盘，两者可能同时认领同一块，因此 CAS
必须保留。状态名不必改。

### 6.2 需要一并修正的两个行为

1. **`Owning` 必须写自定义 `Drop`**，把 `Owning → Created`。现在 `Owning` 根本没有 `Drop`，
   状态会永远停在 `Owning`，README 的示例无法通过。
2. **`try_sharing` 要支持"已经是 `Sharing` 就加计数"**。README 示例在泄漏一个 `Sharing` 之后
   仍断言 `retain.try_sharing().is_some()`，而当前实现只允许 `Created → Sharing`。
   `try_owning` 则继续只接受 `Created`（必须有"无强引用"判据）。

- 集成测试 `tests/pre_drop_.rs`：类型级生效、对象级覆盖类型级、跨子域共享，3 个用例全绿；
- `cargo test -p sw-scope`：**lib 34 + 集成 3，全绿**。

**遗留 / 阻塞**：

| 项 | 状态 |
| --- | --- |
| `try_emplace_with` | **阻塞**：`TrEmplace::emplace(layout, place: *mut Target)` 对 `?Sized` 目标拿不到元数据（要构造 `*mut Target` 就得先有元数据，循环），且 `Result<'f>` GAT 定义了却没用上。要先重定 `TrEmplace` 的形态（与 D4 的 `?Sized` 元数据问题同源） |
| `try_put_str` | **阻塞**：`ScopeStr` 是空结构体，无处存字符串；需先定其形态（DST？），属公开 API 决策 |
| 清盘来源 (b) | `reclaim_strong_pools_` 已具备整块回收能力，但还没有"域静默 / 显式 `collect()` → 遍历存活链逐个 `PreDrop` + 析构 → 回收"的驱动 |
| 弱池扩容 | `allocate_weak_` 只走"链尾还有空位"，满链返回 `None` |
| `Scope` 的生命周期 | `Scope` 还没有 `Drop`，子域内存目前会泄漏；"所有 `Retain` 消失后回收整棵树"尚未实现 |

**并发限制（重要，待决策）**：类型级注册表目前**没有任何同步**。`Scope::set_pre_drop` 经
`root_registry_mut_` 拿 `&mut PreDropRegistry`，而它由 `set_pre_drop` 的 `&mut Scope` 独占性
背书——但同一棵树可以有多个 `Scope`（父 / 子 / 兄弟），跨线程同时 `set_pre_drop` 或
"一边注册一边放入"就会造成 `Vec` 上的数据竞争（UB）。可选修法：给注册表加自旋锁 / 只允许
在"无并发"阶段注册 / 把注册挪到编译期 trait。本轮的集成测试用一把互斥锁串行化以规避。

分配管线的最小闭环（按依赖顺序）：

1. **语义修正**：`Owning::drop` → `Created`；`Sharing::clone/drop` 增减强计数、归零回 `Created`；
   `Retain::clone/drop` 增减弱计数、归零且无强引用时走来源 (a) 认领销毁；`try_sharing` 支持
   `Sharing → Sharing` 增量。
2. **强池分配**：`StrongPool` 的 bump 分配与整块回收（`allocate_` / `free_addr_`）。
3. **槽位与强块的就位构造**：`ScopeInner::allocate` 串起"选池 / 建池 → 分配弱槽位 → 分配强块
   → 就地构造 `T` → `set_record_erased_` → 挂存活链"。
4. **`Scope::try_put` / `try_put_str` / `new_from_parent`**：把 `Retain` 交出去；`demo_::demo`
   必须能跑通（它同时覆盖 `Owning` 析构后仍可再升级、以及泄漏 `Sharing` 后 `try_sharing` 仍成功）。

## 8. 测试计划（中文文档注释，依 AGENTS §2）

- `pre_drop_runs_exactly_once_on_cleanup`：所有外部句柄析构后发起清盘，探针计数必须为 1，
  二次纳入必须失败；
- `pre_drop_runs_on_sweep_for_cyclic_retains`：**本轮重点**——构造两个对象互持 `Retain`
  形成环，验证清盘能纳入它们、且两个钩子各跑一次；
- `pre_drop_runs_on_sweep_after_retain_is_forgotten`：`mem::forget` 后靠清盘兜底；
- `deterministic_destroy_runs_pre_drop_immediately`：`Owning` 析构 + 最后一个 `Retain` 析构
  后，钩子在清盘**之前**就已经跑过——钉死来源 (a) 的"立即"语义；
- `owning_drop_returns_to_created_and_data_stays_alive`：README 示例的最小复现；
- `pre_drop_runs_before_drop`：钩子内读到有效数据、钩子后 `Drop` 计数递增；
- `object_level_hook_overrides_type_level`：同一个 T，一个对象带对象级钩子、一个不带，
  验证对象级只覆盖自己；
- `pre_drop_record_is_shared_per_type`：同一 `T`、同一 `Fin` 类型的两次登记取到同一地址
  （`ptr::eq` 为真）；**不要**断言跨类型地址不等——内容相同的记录允许被编译器合并
  （本轮已用最小程序观察到 `u64` / `u32` 的 `None` 记录合并）；
- `weak_chunk_size_is_type_agnostic`（现有测试）：把期望值更新为 48；
- `unsized_meta_roundtrip`：把现有 `?Sized` 元数据往返测试迁到新布局；
- 编译失败测试（可选）：捕获式闭包必须被 `zst_value_` 的 `const` 断言拒绝。
