# 清盘任务外移：RootScope 的 TeardownTaskPool 与延迟任务节点

- 日期：2026-09-22 19:11
- 模块：`scope_inner_` / `root_` / 新增 `teardown_`
- 状态：**设计草案，未实现**。本文定结构、生命周期、锁边界与重入风险；落地前先评审
  “`live_*` 留域内、只迁 `pending_*`”以及“终结不可逆”这两条决策。
- 相关：`scope-20260922-1423.md`（A 方案与清盘顺序）、
  `rootscope-20260922-1628.md`（RootExtension 与弱池反推）、
  `atomic-20260922-1541.md`（锁原语）、
  `weak-20260922-1135.md`（PreDrop 与“清理列表”）。

## 1. 决策摘要

1. **`live_head_ / live_tail_` 不迁出 `ScopeInner`。**
   它们描述“本域最老 / 最新的仍存活对象”，并跟随本域的 `put` 与对象回收实时变化；
   它们是 `flush_` 与 `is_quiescent_` 的遍历入口，放在域内最直接，也避免每次分配都去
   root 任务节点上做一次间接写。
2. **只把真正冷的 `pending_*` 外移到 root 的 `TeardownTaskPool`。**
   `pending_head_ / pending_tail_` 原本每个 `ScopeInner` 都有一份，但只有 root 上的那份
   有意义；`pending_next_` 只在关闭后的待回收名单中使用。
3. 统一使用 `teardown` 命名：
   - `TeardownTask`
   - `TeardownTaskPool`
   - `teardown_lock_`
   - `pending_teardowns_` / `pending_empty_`
4. **清盘终结语义先定为不可逆：不支持 GC 式 finalize 后复活。**
   `PreDrop` 是最后一次通知；从 hook 中逃逸出去的 `Retain` / `Sharing` 不得让对象重新
   变活。重入 / 复活风险与安全兜底见 §7。

## 2. 为什么 live_* 留域内

`live_*` 不只是“备用清盘数据”：

- 每次 `put` / `try_emplace` / `try_put_str` 都要把新对象挂到本域 live 链尾；
- `Retain` 消失导致的确定性析构、以及 `flush_` 都要沿 live 链遍历；
- `is_quiescent_` 也依赖 live 链判断本域还有没有存活对象；
- 它紧密跟随本域的分配动作，而不是 root 级清盘动作。

若把它迁进 root 任务节点，会引入：

- 首次 `put` 前必须确保任务节点存在，与“pending 任务只在关闭时才需要”的冷数据定位冲突；
- 每次分配多一次 root 任务节点间接写；
- 多线程下 live 链的 owner 是域线程，但任务节点若已挂入 root 队列又会与 root 扫描发生
  可见性问题，需要额外锁或原子字段。

因此第一版只迁 `pending_*`，`live_*` 保留在 `ScopeInner`。后续若要继续压缩
`ScopeInner`，可单独评估把 `chain_*` 或 `live_*` 放进任务节点，不与本轮混做。

## 3. 结构与布局

### 3.1 `TeardownTask`

```rust
#[repr(C)]
pub(crate) struct TeardownTask<const CELL_SIZE: usize> {
    /// 任务属于哪个域。任务进 pending 队列后，扫描者靠它找回 ScopeInner。
    owner_scope_: NonNull<ScopeInner<CELL_SIZE>>,

    /// pending 队列的 next；任务空闲时复用作 pool 空闲链 next。
    next_: Option<NonNull<TeardownTask<CELL_SIZE>>>,

    /// 在本任务池中的槽位序号，供任务地址 O(1) 反推所属池。
    pool_order_: PoolIndex,
}
```

任务不保存 `live_*`。清盘遍历仍回到 `owner_scope_` 读取 `ScopeInner.live_head_`。

### 3.2 `TeardownTaskPool`

与 `WeakPool` 同套路：池头 + 内嵌槽位数组 + 空闲链 + 兄弟池链。

```rust
pub(crate) struct TeardownTaskPool<const CELL_SIZE: usize> {
    capacity_: PoolIndex,
    used_length_: PoolIndex,

    /// 空闲任务链表头；用每个任务的 `next_` 串起来。
    latest_free_: Option<NonNull<TeardownTask<CELL_SIZE>>>,

    /// 同一 root 下的兄弟池。
    prev_: Option<NonNull<TeardownTaskPool<CELL_SIZE>>>,
    next_: Option<NonNull<TeardownTaskPool<CELL_SIZE>>>,

    /// 所属 root，便于从任务节点反推 root。
    root_: Option<NonNull<RootExtension<CELL_SIZE>>>,
}
```

槽位定位用 `pool_order_` 反推：

```text
task_pool = task_addr - (HEADER_BYTES + pool_order_ * TASK_SIZE)
```

任务空闲链只使用 `next_` 指针；因为空闲态和 pending 态互斥，同一字段可以安全复用。

### 3.3 `RootExtension` 新增字段

```rust
pub(crate) struct RootExtension<const CELL_SIZE: usize> {
    weak_pools_: Option<NonNull<WeakPool<...>>>,
    pre_drop_registry_: PreDropRegistry,

    /// 清盘任务池链头。
    teardown_pools_: Option<NonNull<TeardownTaskPool<CELL_SIZE>>>,

    /// 已经“句柄已析构”的任务，等待回收。链表节点是 TeardownTask。
    pending_teardowns_head_: Option<NonNull<TeardownTask<CELL_SIZE>>>,
    pending_teardowns_tail_: Option<NonNull<TeardownTask<CELL_SIZE>>>,

    /// 没有 live 对象、因此没有 TeardownTask 的空域；句柄已析构后挂这里。
    /// 复用 ScopeInner 的 prev_sibling_ / next_sibling_ 作为队列链接。
    pending_empty_head_: Option<NonNull<ScopeInner<CELL_SIZE>>>,
    pending_empty_tail_: Option<NonNull<ScopeInner<CELL_SIZE>>>,

    /// 保护 teardown_pools_ + 两个 pending 队列 + 任务空闲链。
    teardown_lock_: SpinMutex<()>,
}
```

### 3.4 `ScopeInner` 精简后

```rust
pub struct ScopeInner<const CELL_SIZE: usize> {
    flags_: AtomicUsize,                         // CLOSED / HANDLE_DROPPED / EMPTY_PENDING
    parent_scope_: Option<NonNull<Self>>,        // 代际结构，保留
    prev_sibling_ / next_sibling_: ...,          // 代际结构；空域 pending 时复用
    first_child_ / last_child_: Option<...>,     // 代际结构，保留

    chain_head_ / chain_tail_: Option<...>,      // 强池链，保留（分配热路径）
    live_head_ / live_tail_: Option<...>,        // 存活对象链，保留（清盘遍历入口）

    teardown_task_: Option<NonNull<TeardownTask<CELL_SIZE>>>, // 唯一外移入口
    allocator_: &'static dyn Allocator,
}
```

删除的字段：

- `pending_head_`
- `pending_tail_`
- `pending_next_`

保留：

- `chain_head_ / chain_tail_`
- `live_head_ / live_tail_`

## 4. 任务生命周期

### 4.1 空域：`teardown_task_ == None`

- 域刚创建时没有对象，也没有 teardown 任务；
- 只要本域从未 `put` 成功，就始终没有任务；
- 关闭时只标记 `CLOSED`，不分配任务；
- 只有“`HANDLE_DROPPED` + `CLOSED` + 没有子域”的空域，才进入
  `pending_empty_`，用 `prev_sibling_ / next_sibling_` 做链接，并置
  `FLAG_EMPTY_PENDING`；
- 回收空域时不需要 `flush_` 对象，只需回收空强池、归还 `ScopeInner` 自身。

关键约束：

> **只把 `HANDLE_DROPPED` 已置位的域放进 pending 队列。**

这样队列里的域不会被持有 `Scope` 句柄的线程继续 `put`，队列扫描不需要和 owner 线程
竞争 `live_*`。句柄还活着的已关闭域不入队，等它自己的 `Scope::drop` 再处理。

### 4.2 首次插入：延迟分配任务

任务只用于 pending，但为了避免在 `Drop` 中分配，选择在**第一次成功插入对象之前**分配：

```text
try_put / try_emplace / try_put_str
    -> reclaim_pending_()
    -> resolve PreDropRecord
    -> ensure_teardown_task_()      // 失败直接返回 AllocError，不留半成品
    -> allocate_weak_()
    -> allocate strong chunk
    -> construct T
    -> push_live_()                 // 仍写 ScopeInner.live_*
```

`ensure_teardown_task_()`：

- 若 `teardown_task_` 已是 `Some`，直接返回；
- 否则从 root `TeardownTaskPool` 取一个节点，写入 `owner_scope_`，置 `next_ = None`；
- 若池满则扩张；底层分配失败则返回 `AllocError`，此时还没有对象被分配。

这样：

- 空域完全不付任务成本；
- 有对象的域在进入分配管线时一次性分配任务；
- 关闭路径不需要分配，不需要在 `Drop` 里处理 OOM。

### 4.3 关闭：按 `HANDLE_DROPPED` 入队

`close_subtree_` 仍按“子先父后、弟先兄后”的非递归顺序遍历，对每个 `cur`：

```text
1. 标记 CLOSED；
2. 从父链摘下；
3. 若 cur.flags_ & HANDLE_DROPPED != 0：
       if cur.teardown_task_ Some(task) => 把 task 接到 pending_teardowns_ 队尾
       else                             => 把空域接到 pending_empty_ 队尾
   否则：
       不接队列；它已被摘成独立子树，等它自己的 Scope::drop 再走关闭/入队
```

这意味着 `Scope::drop` 不能简单用 `if !inner.is_closed_()` 跳过所有工作：一个已经被祖先
关闭、但当时句柄还活着因而**从未入队**的域，必须在自己的 `Drop` 里重新走一遍关闭 /
入队流程。只有“确认已在 pending 队列中”的域才可以跳过。

### 4.4 回收：锁内摘链，锁外清盘

`reclaim_pending_` 分两段：

1. **锁内**：在 `teardown_lock_` 下，把两个 pending 队列整体摘到本地临时链；
2. **锁外**：
   - 有任务节点：`owner` 若 `is_quiescent_()` 为真，则：
     - 遍历 `owner.live_head_`，执行 `try_claim_destroy` + `PreDrop` + `drop_in_place`；
     - 归还弱槽位；
     - 回收强池；
     - 归还 `TeardownTask`；
   - 空域节点：确认 `CLOSED | HANDLE_DROPPED` 且 `last_child_.is_none()` 后，
     直接回收空强池并归还 `ScopeInner`；
   - 不满足条件的节点收集到“回队链”；
3. **锁内**：把“回队链”接回对应队列尾。

因为节点入队前已保证 `HANDLE_DROPPED`，回收阶段不会和 owner 的 `put` 并发修改
`live_*`；可以安全地在锁外遍历并执行 `PreDrop`。

## 5. 并发与锁

`TeardownTaskPool` 和两个 pending 队列都在 root 上共享，必须有 root 级 `teardown_lock_`：

- `ensure_teardown_task_` 只锁任务池的取槽 / 扩张；
- `push_pending_task_` / `push_pending_empty_` 只锁队尾追加；
- `reclaim_pending_` 如 §4.4，锁内摘链、锁外清盘、锁内回队。

不在锁内做：

- `PreDrop` 钩子；
- `drop_in_place`；
- 弱槽位归还；
- 强池 `deallocate`。

`live_head_ / live_tail_` 的修改只发生在 owner 线程的 `put` 路径；由于节点入队前
`HANDLE_DROPPED` 已置位，owner 线程不可能再持有 `Scope` 句柄，因此不需要在每次
`push_live_` 时持有 root `teardown_lock_`。

> 注意：这与 `scope-20260922-1423.md` §8.4 的 root 共享状态锁是同一问题的两面。
> 若后续决定让 `Scope` 跨线程共享，`live_*` 的可见性需要重新审计；本设计目前假定
> `Scope` 仍为 `!Send`，只有 root 任务池与 pending 队列被多线程访问。

## 6. 内存账与收益

以 64 位、当前 `ScopeInner` 约 120 字节为估算：

- 删除 `pending_head_ / pending_tail_ / pending_next_`：**-24 字节**
- 新增 `teardown_task_: Option<NonNull<TeardownTask>>`：**+8 字节**
- `live_*` 保留，不参与本轮变化
- `ScopeInner` 约 **104 字节**

`TeardownTask` 常态大小约：

```text
owner_scope_  8
next_         8
pool_order_   2
padding       6
----------------
合计         24 字节
```

结论：

- **空 Scope**：不分配任务，净省约 24 字节；
- **有对象的 Scope**：`ScopeInner` 省 24 字节，任务多 24 字节，总量基本持平；
- 收益来自“大量空域 / 临时域”以及 pending 状态集中到 root；
- 若后续把 `chain_*` 也移入任务，需要重新算任务大小与收益。

## 7. 重入与“复活”风险

### 7.1 什么情况下会发生

`PreDrop` 钩子收到 `&mut T`，此时数据仍然有效，允许取出 / 释放其中的 `Retain`、
`Sharing` 来打断环。但这意味着 hook 可以把一个 handle **移出对象并保存到外部存储**：

- 如果保存的是对象自己的 `Retain`，对象被“复活”；
- 如果保存的是另一个对象的 `Retain` / `Sharing`，那个对象被“复活”或继续保活；
- 当前 `flush_` 在认领销毁后，只按状态机推进，**不会在归还弱槽位前重新检查
  `weak_count / strong_count`**。

因此当前实现存在一个实际风险：逃逸出去的 handle 可能指向已经归还给 weak pool、
随后又被新对象复用的槽位。`Retain::try_owning` 可能误认领新对象，属于严重安全性问题。

### 7.2 复现用测试草案

可以用“对象持有自己的 `Retain`，PreDrop 再把它挪到 thread-local”构造：

```rust
use std::cell::RefCell;
use sw_scope::{Retain, Scope, TrScope};

struct Resurrect {
    value: u64,
    self_retain: Option<Retain<Resurrect>>,
}

thread_local! {
    static ESCAPED: RefCell<Option<Retain<Resurrect>>> = const { RefCell::new(None) };
}

fn resurrect_hook(obj: &mut Resurrect) {
    if let Some(r) = obj.self_retain.take() {
        ESCAPED.with(|slot| *slot.borrow_mut() = Some(r));
    }
}

#[test]
fn pre_drop_handle_escape_must_not_alias_reused_slot() {
    ESCAPED.with(|slot| *slot.borrow_mut() = None);

    let mut scope = Scope::new();
    scope.set_pre_drop::<Resurrect, _>(resurrect_hook).unwrap();

    let handle = scope.put(Resurrect {
        value: 7,
        self_retain: None,
    });

    // 让对象持有自己 Retain 的一个克隆；weak_count 变成 2。
    {
        let mut owning = handle.try_owning().unwrap();
        owning.self_retain = Some(handle.clone());
    }

    // 只留下对象内部那个 self_retain；weak_count == 1。
    drop(handle);

    // 强制清盘：hook 会把 self_retain 挪到 ESCAPED。
    unsafe { scope.collect() };

    let escaped = ESCAPED.with(|slot| slot.borrow_mut().take()).unwrap();
    assert!(escaped.try_owning().is_none(), "数据已经终结");

    // 再放一个新对象；它很可能复用刚归还的弱槽位 / 强块。
    let fresh = scope.put(Resurrect {
        value: 99,
        self_retain: None,
    });
    assert_eq!(fresh.try_owning().unwrap().value, 99);

    // 旧 Retain 绝不能认领新对象的槽位。
    assert!(
        escaped.try_owning().is_none(),
        "逃逸出的旧 Retain 不能认领复用槽位里的新对象"
    );
}
```

修复前这个测试可能“看似通过”，也可能直接暴露错误；无论哪种，都说明需要明确语义并补上
内存安全兜底。建议先作为 `#[ignore]` 或文档测试存在，修好后再转正。

### 7.3 建议策略：终结不可逆 + 安全僵尸 handle

先定语义：

> **对象一旦被 teardown 认领，就不可复活。**
> `PreDrop` 是最后一次通知；逃逸出去的 handle 可以继续存在，但只能作为“僵尸 handle”：
> `try_owning` / `try_sharing` / `Deref` 都必须失败或明确 panic，不能重新认领任何对象。

实现层建议：

1. **`flush_` 不立即归还弱槽位。**
   当前实现是遍历并逐个 `mark_finalized(); WeakPool::deallocate()`。改为：
   - 先对本次 teardown 集合完成 `PreDrop + drop_in_place`；
   - 收尾时再检查每个槽位的 `weak_count` 与 `strong_count`；
   - 只有 `weak_count == 0 && strong_count == 0` 才 `Finalized` 并归还槽位；
   - 否则进入 `Zombie` 状态，保留弱槽位，禁止复用。
2. **有 `strong_count > 0` 时不能回收强池。**
   逃逸出的 `Sharing` 持有强块指针；否则 `Sharing::drop` / `clone` 会访问已释放内存。
   最保守做法是让当前域转入“故意泄漏”：不回收强池、不归还 `ScopeInner`，直到确认
   所有 zombie handle 消失；宁可泄漏也不能悬空。
3. **把“终结不可逆”写进 `PreDrop` 的安全契约。**
   当前 `PreDrop` 是安全 API，但可以拒绝复活；若不能强制，则至少要把逃逸场景内存安全
   兜底住。若希望复活成为正式语义，就需要引入外部引用追踪 / 可达性判断，这会回到
   tracing 方向，超出当前设计。
4. **长期优化：zombie slot 回收。**
   若不想泄漏，需要从 `WeakChunk` / `TeardownTask` 能找回所属 root 或 weak pool，
   在最后一个逃逸 handle 消失时归还槽位。这正是 `weak-20260922-1135.md` §6.3 提到的
   “每对象多一个 owner 指针”的权衡，可单独设计。

## 8. 不变量

1. `teardown_task_ == None` ⇒ 本域没有成功 `put` 过对象，因而没有 live 数据。
2. 一个 `TeardownTask` 在任一时刻只属于以下一种状态：
   - 空闲在 pool 中；
   - 被某个 `ScopeInner.teardown_task_` 独占；
   - 挂在 root `pending_teardowns_` 队列中。
3. 任务只有在 `owner_scope_` 已置 `HANDLE_DROPPED` 后才允许进入 `pending_teardowns_`。
4. 空域只有在没有 `TeardownTask`、没有子域、且 `HANDLE_DROPPED` 后才允许进入
   `pending_empty_`。
5. `pool_order_` 终生不变，任务归还时只重置 `next_`，不重写 `pool_order_`。
6. root `teardown_lock_` 不包住任何用户代码；回队在锁内做，清盘在锁外做。
7. 被回收的任务节点不得再出现在任何 `ScopeInner.teardown_task_` 中。
8. 终结不可逆：任何进入 `Destroying` 的对象不得回到 `Created` / `Sharing` / `Owning`。

## 9. 与现有 A 方案的关系

- `flags_` 的 `CLOSED` / `HANDLE_DROPPED` 语义不变；
- `ScopeInner.live_*` 与 `push_live_` / `is_quiescent_` / `flush_` 的遍历逻辑不变；
- `reclaim_pending_` 从“遍历 root pending 域链”改成“遍历 root pending 任务 / 空域队列”；
- `pending_*` 从每个 `ScopeInner` 移到 root；
- `Scope::collect` 仍直接对当前域执行 `flush_`，不需要先把域挂到 root 队列。

## 10. 落地步骤建议

1. 新增 `TeardownTask` / `TeardownTaskPool` 与 root 队列、锁字段，先不改变行为；
2. 引入 `teardown_task_` 与 `ensure_teardown_task_`；
3. 改造 `close_subtree_` / `reclaim_pending_` 使用任务队列；
4. 最后删除 `ScopeInner` 的 `pending_*`；
5. 先完成“终结不可逆 + zombie 安全兜底”，再补 PreDrop 复活测试；
6. 评估是否把 `chain_*` 也移入任务。

## 11. 验证清单

- 任务池：初始预分配、扩容、跨池归还、O(1) 反推所属池；
- 空域：创建后不分配任务；关闭后进空域队列；句柄已掉后可直接回收；
- 有对象域：首次 `put` 分配任务；关闭后任务入队；`flush_` 后任务归还；
- `put_after_close`：默认与 `strict-put-after-close` 两种构建行为保持；
- 深层链：10 万层子域关闭仍不爆栈，任务节点与空域节点不泄漏；
- PreDrop 保证路径：环、`mem::forget` 的 Retain 仍能在清盘时各跑一次；
- 重入 / 复活：`pre_drop_handle_escape_must_not_alias_reused_slot` 在修复后必须稳定通过；
- 泄漏型 zombie：逃逸 handle 存在时不得归还弱槽位 / 强池，也不得让新对象复用旧槽位。
