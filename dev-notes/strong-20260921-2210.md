# StrongChunk / WeakChunk 控制块重做

- 日期：2026-09-21 22:10
- 模块：`strong_` / `weak_` / `scope_inner_`
- 状态：结构已落地，存活链与清盘待接

## 1. 推翻的旧模型

更早的一版模型把生命周期关系理解反了，据此写的实现已作废（那篇笔记已随模型废弃而删除，
可在 git 历史中查阅）。错误在于假设：**弱槽位会独立于强块被回收并复用**，因此"存活链不能
挂在弱槽位上"。

正确的关系是：

> **`Retain` 是保活根。** `Owning<'a, T>` / `Sharing<'a, T>` 都是它的伴生视图，`'a` 绑定在
> `&Retain` 上，不可能比产生它的那个 `Retain` 活得更久。所以：数据还活着 ⇒ 至少一个
> `Retain` 活着 ⇒ 这个 `WeakChunk` 活着。

由此，弱槽位是"对象身份 + 生命周期上下文"，**必然比强块的数据区活得久**。存活链的链接、
类型擦除析构的登记、状态与弱计数，全部可以安全地放在弱槽位里。

同时纠正一个概念混淆：`WeakChunkState.weak_state_` 里的**弱**引用计数（多少个 `Retain`）
与 `StrongChunkBase.refc_` 里的**强**引用计数（多少个 `Sharing`）本来就是两个独立的东西，
不是同一个原子字里的两个维度。

## 2. 职责划分

| | `WeakChunk<T>`（弱池） | `StrongChunk<T>`（强池） |
| --- | --- | --- |
| 定位 | 对象身份、生命周期上下文 | 数据单元 |
| 承载 | `DataState`、弱引用计数、空闲链、存活链链接、析构登记 | 用户数据、强引用计数、指回身份的指针 |
| 备注 | 最长寿的一环；用户日常访存不常触碰的元数据都放这里 | 刻意做小，提高 arena 空间效率 |

决策"不复用内存空洞"之后，强块不再需要 `pool_` / `prev_` 之类池内出入记录，因此
`StrongChunkBase` 只剩 `{refc_, weak_chunk_}` 两个字段。

## 3. 实测布局（64 位）

| 结构 | 尺寸 | 说明 |
| --- | --- | --- |
| `StrongChunkBase` | 16 | `AtomicU32` + 弱槽位指针，8 字节对齐 |
| `WeakChunk<T>` | 56 | 与 `T` 无关（`T` 只在 `PhantomData` 里） |
| `WeakPool` 池头 | 32 | 槽位数组从"向上取整到槽位整数倍"处开始 |

`WeakChunk` 的 56 字节构成：`WeakChunkState`(8) + `prev_live_`(8) + `next_live_`(8) +
`strong_chunk_`(8) + `DropVtable`(24) + `PhantomData`(0)。（早先这里误记为 64，与实际
字段求和不符，已按 `size_of` 语义更正；`DropVtable` 的 24 字节账见
`weak-20260922-1135.md` §4.4。）

**教训**：池头大小不再假设"恰好等于 2 个槽位"。`HEADER_SLOT_COUNT` 改为
`size_of::<Self>().div_ceil(SLOT_SIZE)`，槽位数组起点、`min_size_for_max_count`、
`max_count_within_max_size`、`layout_of_` 全部按同一套算法取整——上一版就是因为
"写入用裸池头大小、读取用取整后的槽位偏移"，导致读到的槽位全是未初始化内存。

## 5. 需要写清的前提：位置终身不变

`StrongPool` 是纯 bump 分配，`used_count_` 只增不减，且不给中间空洞做复用。由此得到：

> 一旦给某个对象分配了位置，该位置在对象整个生命周期内都不会移动，也不会被别的对象占用。

对象身份里保存的强块指针、以及存活链上的链接，都建立在这条不变量上。整块池子只在 Scope
静默时一次性回收。

## 7. 状态锁与状态 CAS 的分工（补记）

重做初期我曾把 `WeakChunkStateGuard` 与锁位一起删掉，理由是"状态位上的 CAS 已经保证了
迁移唯一"。这个理由站不住：**CAS 只保护状态位这一个字**，而升级/初始化路径要保护的是一组
彼此相关的写：

- 弱引用计数（`weak_state_` 的低 28 位）
- `WeakChunk.strong_chunk_` 指针
- `WeakChunk.drop_`（析构登记：入口、数据地址、`?Sized` 元数据）
- 强块的 `refc_`

这些字段不在同一个字里，CAS 管不住它们的组合。典型竞态：`try_share` 把状态改成 `Sharing`
之后、`incr_strong_count` 之前，并发的 `Retain::clone` / `Retain::drop` 会看到"已经共享但
强计数还没起来"的中间态；反过来先抬计数再改状态，并发的失败者也可能已经动过强计数。
更根本的是"数据已就位但状态还是 `Reclaimed`"这个窗口——外界会看到半成品。

因此恢复并明确职责划分：

| 机制 | 保证 |
| --- | --- |
| `weak_state_` 上的状态 CAS | **状态迁移唯一**（谁都不许把已生效的状态覆盖掉） |
| `WeakChunkStateGuard`（`weak_state_` 最高位） | **一整段临界区**：读判据 + 一组相关写 |

API：

- `WeakChunk::try_lock(max_try) -> Option<WeakChunkStateGuard>`：有界自旋，失败即返回
  `None`（"尝试性"语义）；
- `WeakChunk::lock_busy() -> WeakChunkStateGuard`：忙等直到拿到锁，无重试上限，供日后
  需要阻塞等待的路径使用（锁总会在守卫析构时释放，不会永久自旋）；
- 守卫 `Deref` / `DerefMut` 到 `WeakChunk`，临界区内可改槽位字段；
- 守卫 `Drop` 释放锁位，**即使临界区内 panic 也一定归还**；
- 归还槽位（`WeakPool::deallocate` → `link_as_freed` → `reset_all`）时断言锁位已释放：
  归还时还锁着说明有线程卡在升级路径里，属于逻辑错误。

一个实现细节：`reset_all`（归还路径，可以对状态做断言）与 `init_unallocated`（首次初始化，
分配器给的是随机字节，不能做任何断言）必须分开。合并成一个会在"初始化未初始化内存"时
误报锁位已置位——这正是最初随机失败的原因。

## 8. 锁的所有权收口（补记）

第 7 节把锁接回来了，但留下了两个问题，现已修正：

1. **存在 `unlock` 方法**。只要"解锁"还能被别处调用，"持锁者一定负责释放"这条不变量就
   无法成立——谁都能把别人的锁放掉。现在**代码里根本不存在解锁入口**：唯一的解锁点是
   `WeakChunkStateGuard::drop`，且它直接对状态字做 `fetch_and(!LOCK_ST_MASK)`，不经过
   任何辅助方法。`WeakChunkState` 上的抢锁原语（`try_acquire_` / `spin_acquire_`）都是
   私有的，外部无法单独抢锁而不接手释放责任。

2. **抢锁与建守卫之间的孤儿窗口**。原先 `WeakChunkState::try_lock` 返回 `bool`、守卫由
   调用方另建，两步之间若有 panic，锁位就永久置位。现在**锁的获取由守卫自己完成**：
   `WeakChunkStateGuard::try_acquire_` / `spin_acquire_` 先算好指针（不 panic），抢锁是
   唯一可能 panic 的步骤且发生在**持锁之前**；抢到之后只剩一次结构体字面量构造
   （指针运算 + `PhantomData`），既不分配也不调用用户代码。因此"锁一旦置位，守卫就已经
   在返回路上"，不存在孤儿锁窗口。

公开入口保持你要求的三个：`try_lock(max_try) -> Option<Guard>`、
`try_acq_state_guard(max_try) -> Option<Guard>`（与状态层命名对应的别名）、
`lock_busy() -> Guard`。

新增测试 `weak_chunk_lock_is_released_when_guard_drops_during_panic`：在 `catch_unwind`
里持锁后主动 panic，验证栈回退时守卫把锁带走、之后仍可重新上锁。

## 9. 原子操作收口（参考 `atomic_sync` 的写法）

第 7、8 节把锁接回来了，但抢锁逻辑写了两遍（有界重试一份、忙等一份），条件 CAS 也散在
五处。参考同仓库 `atomic_sync` / `atomex` 的组织方式（`try_once_compare_exchange_weak`
负责一次 CAS，`try_spin_compare_exchange_weak` 只是它的循环封装，并用三态
`CmpxchResult` 区分"判据不成立"与"被别人改动"）收口如下。sw-scope 目前**零依赖**，
因此只借结构、不引 crate：

- `CmpxchResult<T>`：本地定义的三态结果（`Succ` / `Unexpected` / `Fail`），语义与
  `atomex::CmpxchResult` 对齐；
- `WeakChunkState::try_once_(current, desired)`：**全文件唯一一处 `compare_exchange`**；
- `WeakChunkState::update_(desire)`：以闭包给出期望值的收敛循环，"期望值 == 当前值"
  即表示无需改动；失败则用观察到的值重试，不会拿着过期状态空转；
- `WeakChunkState::acquire_(max_try)`：**唯一一处抢锁循环**，`max_try == 0` 表示不限
  次数（忙等）。`WeakChunk::try_lock` / `try_acq_state_guard`（有界）与
  `WeakChunk::lock_busy`（不限）都只是它的两种参数，守卫侧的 `try_acquire_` /
  `spin_acquire_` 也共用同一条路径；
- 释放锁走 `update_`，且只有 `WeakChunkStateGuard::drop` 会调用它；
- 计数增减保留 `fetch_add` / `fetch_sub`：它们本身没有"比较—重试"语义，套进 CAS 循环
  反而是倒退。

收口后 `compare_exchange` 在整个 `weak_/chunk_.rs` 里只出现一次。

## 10. 补齐 7 态 `DataState`

第 4 节重做时我只落回了原版的 5 态，漏掉了本文档 §7.1 已定的另外两态。现已补齐：

| 状态 | 值 | 含义 |
| --- | --- | --- |
| `Reclaimed` | 0x00 | 未使用 / 已可复用，弱槽位空闲 |
| `Created` | 0x01 | 已分配，仅被 `Retain` 持有 |
| `Owning` | 0x02 | 被 `Owning` 独占持有 |
| `Sharing` | 0x03 | 被 `Sharing` 共享持有 |
| `Destroying` | 0x04 | 已认领销毁，`Drop` 尚未执行完毕 |
| `Destroyed` | 0x05 | 数据已析构，内存待清盘回收 |
| `Finalized` | 0x06 | 已退出存活链、弱计数归零，可随池一并回收（"已纳入 GC 队列"的终态） |

`is_data_alive()` 仍然只认 `{Created, Owning, Sharing}`；另加 `is_claimable()` 表达
"还能被认领销毁"（当前等价于 alive，单独命名是为了让调用点的意图明确）。

迁移入口收口在 `WeakChunkState::try_update_state_(desire)`：闭包接收当前状态，返回
`None` 表示前提不成立、返回同值表示已就位，其余情况做一次只改状态位、保留引用计数的 CAS。
在此之上的语义方法：

- `try_claim_destroy()`：`{Created, Owning, Sharing} → Destroying`，**认领唯一**，
  是多路径析构下"恰好销毁一次"的唯一裁决点；
- `mark_destroyed()`：`Destroying → Destroyed`（只有认领者调用）；
- `mark_finalized()`：`→ Finalized`（清盘收尾）；
- `init_created()` / `try_set_state(to)`：升级路径用的 `Created` 置位与条件迁移。

测试覆盖：`weak_chunk_data_state_full_transition_path`（`Created → Owning → Destroying →
Destroyed → Finalized`，含重复认领必须失败）、
`weak_state_sharing_path_claims_destroy_exactly_once`（`Sharing` 路径）、
`weak_state_upgrade_primitive_is_exclusive`（升级判据唯一）。

> **注意**：以上只说明"状态怎么迁移"，不说明"什么时候迁移"。`Destroying` 的触发条件是
> **对象进入清理列表**——来源为"计数不可达"或"清盘强制纳入"两种（以
> `weak-20260922-1135.md` §2、§6 为准）。旧笔记里"`Owning::drop` 与 `Sharing` 归零即析构"
> 的写法既与 README 的使用思路矛盾，也漏掉了"环/泄漏只能靠清盘"这一保证路径，已废弃。
