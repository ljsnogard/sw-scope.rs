## 0. 现行模型：StrongChunk 与 WeakChunk 不再一一对应

这是本次重构的核心，也是阅读其余所有内容的前提。

### 0.1 两条创建路径

```text
        ┌── 直接构造（如 Owning::try_new_local）──> Owning<'a, T, M>
Scope ──┤
        └── 直接构造 ────────────────────────────> Sharing<'a, T, M>

Retain<T, M>
    ├── try_owning()  ──> Owning<'a, T, M>
    └── try_sharing() ──> Sharing<'a, T, M>

Owning / Sharing ──retained()──> Retain<T, M>   （首次调用时补建 WeakChunk）
```

- 直接构造的句柄，其 `'a` 借用产生它的 `&'a mut Scope`；
- 由 `Retain` 升格的句柄，其 `'a` 借用 `&'a Retain`；
- 两条路径都不能让句柄逃逸成任意长生命周期的所有权结构，这正是“不扫描可达性也能清盘”的
  前提。

### 0.2 强块与弱槽位的关系

- 对象本体的强块（`StrongChunk`）**不一定**有弱槽位（`WeakChunk`）：直接构造的对象没有。
- 只有 `retained()` 需要产生 `Retain` 时，才为强块补建一个 `WeakChunk`。
- 一旦补建，强块上那个“身份槽位”指针终生不变：只要强块还活着，这个 `WeakChunk` 就一直
  存在，不会消失、不会改指、不会被回收复用。

由此，旧模型里那条被当作地基的不等式被替换：

```text
旧：数据还活着 ⇒ 至少有一个 Retain 活着 ⇒ 这个 WeakChunk 还活着
新：WeakChunk 活着 ⇒ 它对应的 StrongChunk 活着；反之不成立
```

**推论（写文档、写代码时都要遵守）**：

- 凡把“对象必然有 `WeakChunk` / `Retain`”“`Owning` / `Sharing` 必然借自 `Retain`”当作
  普遍前提的表述都已过时；
- 凡要经弱槽位完成的工作（存活链、清理登记、由槽位反推弱池 / root），都必须先确认
  `StrongChunk::weak_chunk()` 是 `Some`；
- 无弱槽位的对象不走弱槽位这条路径，它就是普通的 arena `Box` / `Arc`。

### 0.3 谁是生命周期权威

| 情形 | 数据何时析构 | 语义类比 |
| --- | --- | --- |
| 无 `WeakChunk` | 最后一个强句柄析构时当场析构 | `Box<T>` / `Arc<T>` |
| 有 `WeakChunk` | 强计数归零**不**析构；由最后一个 `Retain`（确定性路径）或 Scope 清盘（保证路径）负责 | `Retain` + 状态机 |

有弱槽位时状态机里还会出现 `Zombie`：数据已经析构，但仍有逃逸的 `Retain`，此时弱槽位不得
复用，要等最后一个逃逸句柄消失才归还 `WeakPool`。

### 1.1 `abs_`：面向用户与内部的抽象接口

- `TrScope`：`try_emplace_with` / `try_alloc_slice_uninit` / `set_pre_drop`。目前只实现
  `&mut Scope<Local>`。
- `TrScopeExt`：在 `TrScope` 之上的便捷组合（`try_put` / `try_put_str` / `try_clone` /
  `try_put_with` / `put` / `put_with` / `put_str`）。`?Sized` 的公开入口目前是 `todo!()`。
- `TrPreDrop<T>`：对象进入清理列表时的最后通知；`()` 是空实现。
- `TrShareMarker`：线程模式 marker 的约束边界（`impl(crate)`，外部不可实现）。

原则：面向用户的 trait 尽量薄，落地路径都收敛到 `try_emplace_with` 这一条分配管线。

### 1.2 `emplace_`：就地构造

`TrEmplace::emplace(layout, place)` 在一个已经划好的数据区上就地写入 `Target`。
`IntoEmplace` 用“收到胖指针后自己写入”的闭包实现它。就地构造的意义：避免“先建在栈上再搬
进 arena”，也支持自引用结构。

### 1.3 `share_marker_`：线程模式

`Local` 是当前唯一实现的模式（`!Send + !Sync`），`Shared` 只是预留的类型占位。
单线程优先的理由见 §2.7。

### 1.4 `scope_`：用户侧 `Scope`

- 用户拿到的 `Scope` 永远是内部 `RootScope` 的子域；`RootScope` 不会作为 `Scope` 返回。
- `Scope::new_local()` 用默认 root 创建子域；`try_config_root(...)` 只初始化 root 并返回
  是否由本次调用完成初始化。
- `collect()` 是显式清盘入口；`Drop` 只做“标记关闭 + 摘链 + 挂待回收名单”，真正的析构与
  回收发生在“句柄已析构 + 已关闭 + 静默”之后，因此 `Drop` 保持 safe。
- `set_pre_drop::<T, Fin>()` 在本 Scope 树里做类型级注册；表挂在 root 上，子域注册对父 /
  兄弟同样可见。

### 1.5 `scope_tree_`：域树与分配管线

按“紧密共享同一组字段的操作放在一起”拆分：

| 文件 | 内容 |
| --- | --- |
| `mod.rs` | 常量、`PoolIndex`、默认 root 发布点与逐项导出 |
| `tree_node_` | `TreeNodeBase`：父子 / 兄弟链（代际结构），手动模仿“继承” |
| `scope_node_` | `ScopeNodeExt`（标志、子链、强池链、存活链、分配器引用）与强池 bump 分配 |
| `root_node_` | `RootScope` / `RootNodeExt`：共享扩展 + 内联分配器 + 一次性初始化 + 由域定位 root |
| `teardown_` | 清盘方案 A 的关闭 / 静默判定 / 待回收名单（跨线程任务池见 §4） |

关键布局决策：`RootScope<A>` 是 `{ tree_node_, root_ext_, allocator_ }`，分配器永远放最后。
每个域只存一个 `&'static dyn Allocator`，指向 root 的分配器字段；回退固定偏移即可得到
`RootNodeExt`，不需要知道 `A`，空域也成立。

### 1.6 `scope_str_`：arena 里的 `str`

`ScopeStr(str)` 保持 `str` 的 DST 形态，因此 `Retain<ScopeStr>` / `Owning<ScopeStr>` 的
`?Sized` 元数据就是长度，`&*句柄` 直接是 `&str`。放入走 `EmplaceScopeStr`。

### 1.7 `strong_`：强块与强池

- `StrongChunk<T> = StrongChunkHead + T`。头部只含两样：强引用计数（供 `Sharing`）与
  **可空**的身份弱槽位指针。
- 强池 `StrongPool` 是纯 bump 分配：位置一旦分配终身不变，不给中间空洞做复用；整池只在域
  静默时一次性回收。对象身份所依赖的“地址稳定”就建立在这条不变量上。
- 直接构造（无弱槽位）时，强块自己就是生命周期权威：最后一个强句柄析构即就地析构。

### 1.8 `weak_`：弱槽位、弱池与 `PreDrop`

- `WeakChunk<T>` 是对象身份槽位：`Retain` 指向它；一旦建立就与强块同寿（§0.2）。
  它还是存活链链接、清理登记与 `?Sized` 元数据的落点。
- `DataState` 是**有弱槽位时**“数据要不要析构”的唯一权威；`try_claim_destroy` 的 CAS 是
  这条路径上“恰好销毁一次”的唯一裁决点。
- `WeakPool` 是内嵌式槽位池：池头 + 槽位数组 + 空闲链；`pool_order_` 终生只读，因此可由
  槽位地址 O(1) 反推所属池。槽位尺寸与 `T` 无关，池按 `WeakChunk<()>` 步长定位。
- `PreDropRecord` 是“该类型进入清理列表时怎么处理”的类型级登记，只含一个类型擦除入口；
  每个 `T`（或 `(T, Fin)`）经“关联常量 + 取引用”只生成一份静态记录。
- `PreDropRegistry` 是按类型 ID 查找的树级注册表（键见 §3.1）。

### 1.9 `smart_pointer_`：三种句柄

- `Owning<'a, T>`：独占访问。直接构造时是 `Box` 语义；由 `Retain` 升格时只归还访问权。
- `Sharing<'a, T>`：引用计数共享。无弱槽位时是 `Arc` 语义；有弱槽位时强计数归零只归还访问权。
- `Retain<T>`：可选的身份句柄，也是升级入口（`try_owning` / `try_sharing`）。它自己持有
  弱计数，因此只要句柄活着，`WeakChunk` 就不会被回收。
- 三者当前都只在 `M = Local` 上实现，且保持 `!Send + !Sync`。

### 1.10 `atomic_`：原子原语与自旋锁

- `cell_`：`TrAtomicCell` / `TrAtomicData` / `TrBitWord` / `TrCmpxchOrderings`，把
  `AtomicU32` / `AtomicUsize` 统一成字宽原子量。
- `signal_`：“哪一位是锁信号”的策略 `TrMutexSignal`（默认最高位 `MsbAsMutexSignal`）。
- `spin_`：`SpinMutex<T>`（锁住任意内容）与 `SpinFlag`（锁住“锁位 + 业务位”的同一字）。
- **CAS 只出现在这里**；业务代码只看到“抢锁 / 释放 / 条件读改写”这些语义操作，
  解锁只发生在守卫的 `Drop` 里。

### 1.11 `demo_` 与对照实验

- `demo_.rs` 是 `#[cfg(test)]` 的使用示例（README 示例的可执行版本）。
- `drop-semantics-demo/` 是独立 workspace：用 `bumpalo` 实证“谁负责析构”决定了哪些普通
  写法会泄漏（§3.3）。

## 2. 设计原则（仍然有效）

### 2.1 不做 tracing GC

只用 Rust 生命周期约束“临时访问”，用引用计数回答“还有没有人正在访问”；不扫描对象图，
不实现标记-清扫。

### 2.2 触发终结的是“进入清理列表”，不是“最后一个引用释放”

```text
纳入清理列表
    → 1) 运行 PreDrop 钩子（数据仍然有效，可 &mut）
    → 2) drop_in_place（真正的析构）
    → 3) 标记已销毁；空间随清盘整块回收
```

两条来源，都跑 `PreDrop`：

| 来源 | 条件 | 时机 |
| --- | --- | --- |
| (a) 确定性析构 | 计数已经证明不可达（有弱槽位：弱计数与强计数都为 0；无弱槽位：最后一个强句柄析构） | 立即 |
| (b) 清盘强制纳入 | Scope 清盘时对象仍存活（环、`forget`、泄漏） | 清盘时 |

引用计数**不能**回答“该销毁了吗”（环、`mem::forget`、泄漏的 `Sharing` 都会让它永不归零），
只能回答“还有没有人正在访问”。

> 尚未定案的一处：现行代码把 `PreDropRecord` 与存活链都放在 `WeakChunk` 上。无弱槽位的对象
> 既没有地方存放清理登记，也因此在就地析构时无法运行 `PreDrop`。`retained()` 补建弱槽位是否
> 也应当承担“登记清理”的职责，或登记要改挂到强块，是这次重构需要解决的问题，见 §4.8。

### 2.3 类型擦除必须有一条兜底析构路径

清盘只拿得到类型无关的强块头 / 弱槽位，因此必须事先登记“怎么清理”。这正是
`PreDropRecord` 存在的全部理由；登记按类型去重，槽位只存一个 `&'static` 指针。

记清一个反直觉的字节账：**共享登记本身并不省槽位字节**（槽位总要放一个指针指出用哪份
登记）；省下的是不再逐对象保存数据区地址。共享的价值在架构位置——`PreDrop` 与 `Drop` 的
合成只写一份，将来新增逐类型操作不再逐对象付费。

### 2.4 `PreDrop` 优先级与约束

```text
对象级钩子  >  类型级钩子  >  没有钩子
```

- 钩子是零尺寸类型（函数项 / 非捕获闭包）且 `'static`；捕获式闭包被编译期 `const` 断言拒绝。
- 钩子运行在数据仍然有效时，收到 `&mut T`，可取出 / 释放其中的 `Retain` 或 `Sharing`——
  这正是环被打断的地方；返回后必须把值留在可析构状态。
- 调用时机唯一：对象进入清理列表且 `try_claim_destroy` 认领成功之后。

### 2.5 恰好销毁一次由 CAS 裁决

`try_claim_destroy` 把状态从存活态搬到“已认领”；只有它返回 `Some` 的路径才执行清理。
多路径（最后一个 `Retain`、清盘、未来跨线程）同时认领同一块时，CAS 保证唯一赢家。

### 2.6 位置终身不变、不复用空洞

强池纯 bump、不搜罗空洞；对象地址在生命周期内稳定。整池只在域静默时一次性回收——这换来
了实现简单与身份指针稳定。

### 2.7 先单线程，线程安全只留类型扩展位

`Root` / `Scope` / `Retain` / `Owning` / `Sharing` 都是 `!Send + !Sync`；不实现 root 弱池、
子链、pending 队列的跨线程同步。理由与 gc-arena 相同：先把树、清盘、`PreDrop`、槽位生命
周期在单线程下做正确，避免同时处理“类型擦除 arena 的 Send 条件”和“全树结构锁”。

### 2.8 root 真正持有树级共享资源

弱池链与类型级注册表挂在 `RootNodeExt` 上，整棵树共享一份；各域只存一个指向 root 分配器的
擦除指针用于反推。这样归属名实相符，也避免每域白背指针。

### 2.9 终结不可逆，逃逸句柄只能变 zombie

对象一旦进入清理，就不能复活。逃逸出去的 `Retain` 不允许认领复用槽位里的新对象，因此数据
析构后弱槽位进入 `Zombie` 并禁止复用，直到最后一个逃逸句柄消失才归还。

## 3. 重要经验（踩过的坑与实证）

### 3.1 不能拿“每类型一份常量的地址”当类型身份

编译器会合并内容完全相同的常量（`u64` 与 `u32` 的无钩子记录地址会相同），一旦拿地址当键，
不同类型的钩子就会串味。`core::any::type_name` 也不保证唯一，标准库 `TypeId::of` 又要求
`T: 'static`。因此引入 `typeid` crate：`typeid::of::<T>()` 对非 `'static`、`?Sized` 的 `T`
同样可用。注册表容器用 `BTreeMap`。

### 3.2 `pool_order_` 是换算的一部分

由槽位反推所属池时，第一版只减了池头字节，于是除 0 号槽位外都落在池中段，读出垃圾 `root`。
教训：槽位序号是 O(1) 反推公式的一部分，不是装饰性诊断字段。池头大小还要按槽位大小向上
取整，否则“写入槽位”和“读取槽位”会落在两块地址上。

### 3.3 “谁负责析构”决定泄漏边界

对照实验 `drop-semantics-demo`（用 `bumpalo::Bump`）实测：

| 普通写法 | “从不兜底” | “最后一个句柄负责” | 清盘兜底 |
| --- | --- | --- | --- |
| 匿名临时句柄 | 泄漏 | 正常 | 正常 |
| `?` 提前返回 / panic 展开 | 泄漏 | 正常 | 正常 |
| `mem::forget` 句柄 | 泄漏 | **泄漏** | 正常 |
| `Sharing` 互引成环 | 泄漏 | **泄漏** | 正常 |

结论：**清盘兜底是唯一在表中所有普通写法下都不漏的一支**，而它要求清盘能在不知道 `T` 的
情况下析构——这就是类型擦除登记存在的理由。环不会导致清盘漏 `Drop`，只会把回收推迟到清盘。

### 3.4 与 gc-arena 的对照

- 两者都必须同时有“即时路径”和“类型无关的兜底路径”；
- `gc-arena` 用它头部 `is_live` 标志位保证恰好析构一次，sw-scope 用 `DataState` 的认领 CAS；
- `gc-arena` 的 `CollectVtable` 用“关联常量 + 取引用”提升为每类型一份，sw-scope 的
  `PreDropRecord` 直接借鉴了这一写法；
- 命名上明确不采用 `Finalization` / `finalize` 这类与 `Drop` 混淆的词，统一叫 `PreDrop`。

### 3.5 README 的“泄漏一个 `Sharing` 后仍能继续共享”

`try_sharing` 对已经处于共享状态的对象做**幂等加计数**，因此泄漏一个 `Sharing` 之后仍能继续
共享，只是下一次 `try_owning` 会失败。这是现有语义的一条有意设计。

### 3.6 旧模型的最大教训

把“每个对象必然有 `WeakChunk` / `Retain`”当地基，会让所有“由弱槽位反推”“数据活着⇒弱槽位
活着”“`Owning`/`Sharing` 必然借自 `Retain`”的推导在直接构造路径上失效。现行模型改为
“弱槽位可选、且一旦建立就与强块同寿”，所有相关推导都必须显式分支。

### 3.7 `atomic_` 第一版为什么被否决

第一版把“原子原语 + 锁”混在一个文件里，业务侧（`WeakChunkState`）直接调用 CAS、自己算锁位
掩码。被否决的理由（保留为“为什么不这么做”）：命名太泛（`Spin` 表达不出锁的是数据）；锁信号
位没做成配置项；锁住的内容没通过泛型体现；`compare_exchange` 泄漏进业务逻辑；`atomic_` 与
`spin_` 模块重复。收口后的形态见 §1.10。

## 4. 演进方向（尚未落地）

1. **`SharedScope`**：`T: Send + Sync` 插入约束、每父域子链锁、root 弱池 / 注册表 /
   teardown task 锁、`SharedScope: Send + Sync` 的安全条件。当前只保留 `Shared` marker。
2. **`?Sized` 公开入口**：`Scope::try_clone` / `try_alloc_slice_uninit` 仍是 `todo!()`。
   `?Sized` 元数据有三种、性质不同，因此归属要分开谈：
   - `Sized`：元数据是 `()`，零字节，无需存储；
   - `[E]` 切片：长度逐对象，**不能**同类型共用；但它在分配时已知，可以记为强块头上的长度字，
     位置从弱槽位换到强块头，总量不变；
   - `dyn Trait`：虚表取决于**具体实现类型**。若记录按具体类型 `C` 建立，则对固定的 `C`
     它是类型常量，可以放进“每具体类型一份”的记录里共用。

   现行建议是**暂不决策**，先保留槽位的 `meta_`：`?Sized` 入口还没跑通，统一槽位避免了“按
   元数据种类分支”的复杂度，收益（48 → 40 字节）在入口落地前属于提前优化。
3. **清盘任务外移**：把真正冷的 pending 队列外移到 root 的 `TeardownTaskPool`，`live_*`
   留在域内；任务在首次成功放入时分配，关闭路径不分配。与 `SharedScope` 的锁一起做。
4. **局部 root / 线程本地 root**：消除 `Scope::new_local()` 对进程级全局 root 的共享。
5. **僵尸强块**：若把 `Box::leak(Retain)` 后构造的 `Sharing<'static>` 也纳入保证范围，
   需要同时看 `strong_count`，把逃逸的强块转成受控泄漏或僵尸强块。
6. **可捕获环境的钩子**：唯一不倒退的扩展是把 `Fin` 值存进强块，逐对象多付
   `size_of::<Fin>()` 字节；当前不做。
7. **直接构造路径补全**：`Owning::try_new_local` / `try_local_str` / `retained()`、
   `Sharing` 的对应入口与 `retained()` 目前都是 `todo!()`，需要按 §0 的模型落地。
8. **无弱槽位对象的 `PreDrop` 与清理登记**：`PreDropRecord`、存活链目前都挂在 `WeakChunk`
   上，而无弱槽位的对象没有它。需要决定是“登记随 `retained()` 落位、无 `Retain` 的对象
   不跑 `PreDrop`”，还是把登记与存活链改挂到强块 / 强池，让每个对象都能独立被清盘纳入。
