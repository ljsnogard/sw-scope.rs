# 类型擦除析构登记的按类型去重（DropVtable 上移 RootScope）

- 日期：2026-09-21 21:50
- 模块：`strong_` / `weak_` / `scope_inner_`
- 状态：**方案待评审，尚未动代码**

## 1. 需求

`StrongChunk` 的数据区里放着用户类型 `T`。析构必须发生**恰好一次**，而触发它的路径有三条：

1. `Owning::drop`（独占持有者释放）；
2. `Sharing::drop` 把强计数减到 0（最后一个共享持有者释放）；
3. Scope 清盘的兜底 sweep（数据早已无人引用，但从未被析构）。

前两条路径**手里有类型**：`Owning<'a, T>` / `Sharing<'a, T>` 本身是 `T` 的单态化类型，
`drop_in_place` 可以直接调用，不需要任何类型擦除信息。第三条路径**手里没有类型**：清盘
流程拿到的只是"一块待处理的记录"，必须靠事先登记的信息才能知道怎么析构。

同时我们要求：清盘必须能分辨"该 Drop 却还没 Drop 的"与"已经被智能指针 Drop 过的"，
否则会重复析构或漏掉。这就是"分布式的销毁职责 + 集中的兜底"这一对需求的由来。

## 2. 资料调研：支持 Drop 的 arena 都是怎么做的

| 实现 | 析构如何被触发 | 是否保留逐对象类型信息 | 关键事实 |
| --- | --- | --- | --- |
| [`bumpalo::Bump`](https://docs.rs/bumpalo/latest/bumpalo/struct.Bump.html) | **不触发**。文档明确写 "Objects that are bump-allocated will never have their `Drop` implementation called" | —— | 纯 bump，`Bump::drop` 只释放 chunk 内存 |
| [`bumpalo::boxed::Box`](https://docs.rs/bumpalo/latest/src/bumpalo/boxed.rs.html) | `Box` 析构时 `drop_in_place(self.0.as_ptr())` | **不需要**：类型在 `Box<'a, T>` 的类型参数里 | 类型擦除被编译器完成了，句柄自带 `T` |
| [`arena_lib::DropArena<T>`](https://docs.rs/arena-lib/0.5.0/arena_lib/drop_arena/index.html) | 每个 chunk 是一个 `Vec<T>`，arena / chunk 析构时由 `Vec` 逐个 Drop | **不需要**：整个 arena 只有一个 `T` | 同构 arena，用容器类型承载 `T` |
| [`rustc_arena::TypedArena<T>`](https://docs.rs/rustc-arena-modified/0.1.1/src/rustc_arena_modified/typed_arena.rs.html#631) | `Drop` 里按 chunk 对已初始化区间 `drop_in_place`，非末块用 `chunk.destroy(entries)` 整块析构 | **不需要**：`TypedArenaGen<T, _>` 的单态化给出元素大小与析构 | 同构 arena；非末块已满，可整块 memcpy 式析构 |
| `typed-arena` | 同上（同构、按 `T` 单态化） | 不需要 | 只接受 `T: Sized` 且同构 |
| [`gc-arena`](https://docs.rs/gc-arena/latest/src/gc_arena/types.rs.html) | **两条路径都有**：`Gc<T>` 析构只递减标记；`Context::drop`（arena 终结）与 `Phase::Sweep` 里 `drop_in_place` | **需要**：每个对象的 GC 头里存一个 `tagged_vtable`，指向类型静态的 `CollectVtable` | 见 §2.1 |

**调研结论**：是否"逐对象保存类型信息"，取决于该实现有没有一条**类型无关的兜底析构路径**：

- **同构 arena**（`DropArena`、`TypedArena`、`typed-arena`）：整个 arena 只有一个 `T`，
  类型由类型参数承载，连"记录"都不需要；
- **手写句柄自带类型**（`bumpalo::boxed::Box`）：析构在句柄 Drop 时发生，类型擦除由编译器
  完成，因此完全不需要范围级的兜底；
- **`gc-arena`**：像 sw-scope 一样同时有即时与兜底两条路径，因此**必须**有类型无关的兜底
  析构，做法是每个对象存一个指向静态 `CollectVtable` 的指针（§2.1）。

所以正确说法不是"没人需要逐对象类型信息"，而是：**需要它的实现，都把"怎么析构"和对象
绑在了一起**（`gc-arena` 绑在 GC 头上）。sw-scope 的兜底路径同样必需——`Retain` 是 GC
Handle 式的长期句柄，对象可能先失去所有引用、再等 Scope 清盘——因此类型擦除登记是必需的；
本方案要做的只是**把这份登记按类型去重**，而不是取消它。

顺带得到一条重要对照：**"类型信息该由谁承载"决定了是否需要记录**。`Box<'a, T>` 用句柄
承载，同构 arena 用类型参数承载，而 sw-scope 的兜底路径两者都没有，所以只能显式记录。

### 2.1 `gc-arena` 的做法（最贴近我们的对照）

`gc-arena` 是我们讨论过的最接近的一个：它**同时有**"即时析构"与"兜底析构"两条路径，
并且同样要求"恰好析构一次"。

它的机制（来源：[`types.rs`](https://docs.rs/gc-arena/latest/src/gc_arena/types.rs.html)、
[`context.rs`](https://docs.rs/gc-arena/latest/src/gc_arena/context.rs.html)）：

1. **每个类型一份静态 vtable。** `CollectVtable { trace_value, drop_value, value_layout }`
   在分配点由 `CollectVtable::vtable_for::<T>()` 单态化出来，是 `const` 提升进静态内存的
   一份**共享常量**，不是每对象一份。

   ```rust
   drop_value: |ptr| unsafe { ptr::drop_in_place(ptr.cast::<T>()) },
   ```

2. **每个对象的 GC 头里存一个指向该 vtable 的指针**（`tagged_vtable`），并用它的低位
   （vtable 声明为 `#[repr(align(16))]`）携带 4 个标志位：
   - bit 0-1：`GcColor`（White / WhiteWeak / Gray / Black）；
   - bit 2：`needs_trace`；
   - bit 3：**`is_live`**。

3. **`is_live` 就是"析构是否已经跑过"的认领标志。** `GcHeader::is_live` 的文档写得很直白：
   "When we garbage-collect a `GcPtr` that still has outstanding weak pointers, we set `alive`
   to false... When there are no more weak pointers remaining, we will deallocate the `GcPtr`,
   but skip dropping the value (since we've already done it)." 这正是我们在 `DataState` 里用
   `Destroying → Destroyed` 表达的同一件事。

4. **兜底发生在两处**：
   - `Context::drop`（整个 arena 终结）：`DropAll` 遍历全部对象，`if header.is_live() { drop_in_place(); }`，
     随后 `dealloc()`；
   - `Phase::Sweep`：白对象 `drop_in_place + dealloc`；`WhiteWeak` 对象
     `drop_in_place` 后把 `is_live` 置 false，但**保留分配**，让弱指针还能查存活状态，
     等弱指针全部消失才真正 `dealloc`（此时因 `is_live` 已为 false 而跳过析构）。

5. **`Gc<T>` 本身不实现 `Drop`。** 释放一个 `Gc` 指针只是丢掉一个 `Copy` 值，什么都不会
   发生；析构只可能由"弱指针归零"或"arena 终结 / sweep"触发。

6. **需要类型无关的析构吗？需要。** sweep 走的是 `GcPtr<()>`（类型擦除）链表，
   所以必须靠头里的 vtable 才能拿回 `drop_value`。

### 2.2 与 sw-scope 的逐项对照

| 维度 | `gc-arena` | sw-scope（本方案） |
| --- | --- | --- |
| 何时回收 | 标记-清扫判定不可达 | 引用计数归零 / Scope 清盘 |
| 即时析构路径 | 弱指针归零时的 sweep 分支 | `Owning::drop` / `Sharing::drop` |
| 兜底析构路径 | `Context::drop` 与 `Phase::Sweep` | 清盘 sweep |
| 恰好一次的手段 | 头部 `is_live` 标志位 | `DataState` 的认领 CAS |
| 类型无关析构 | 需要（sweep 走 `GcPtr<()>`） | 需要（清盘只拿到弱槽位） |
| **析构入口存在哪** | **每个对象的 GC 头里一个 vtable 指针** | 计划：每类型一份 `TypeRecord`，槽位只有一个指针 |
| 死对象的弱指针 | `WhiteWeak` 保留分配、`is_live=false` 防空转 | 弱槽位保留到"数据已析构且无 `Retain`" |

**结论**：`gc-arena` 证实了我们前面几条判断——(a) 即时与兜底两条路径都要有；(b) 兜底路径
必须能在类型擦除的前提下析构；(c) 需要一个"析构已跑过"的认领标志避免重复。(d) 顺带也证实了
"环不是例外"：`gc-arena` 靠标记清扫处理环，sw-scope 靠清盘兜底处理环。

**一处它比我们更省、一处我们比它更省**：

- 它把"每类型一份的 vtable"做成了静态常量，这一点和我们要做的一样；
- 但它仍然**每个对象存一个 vtable 指针**（用于从 `GcPtr<()>` 找回 `drop_value`）。我们的
  方案里这个指针也只在槽位里存一份，且弱槽位本来就存在，所以并不是额外开销；换句话说，
  §4 的两级结构在"存一个指针"这一点上与 `gc-arena` 持平，省下的是 `drop_fn`/`offset`/`meta`
  三个字中除指针之外的部分。

## 3. sw-scope 的两条析构路径

| 路径 | 谁触发 | 有无 `T` | 需要的信息 |
| --- | --- | --- | --- |
| 提前析构 | `Owning::drop` / `Sharing::drop` | **有**（句柄是 `Owning<'a, T>` / `Sharing<'a, T>`） | 只需单态化的 `drop_in_place::<T>` |
| 清盘兜底 | Scope sweep | **没有**（只有记录） | 登记信息：析构入口 + 数据区位置 + `?Sized` 元数据 |

现状是两条路径都依赖 `WeakChunk.drop_: DropVtable`，而它**每个槽位一份**：

```text
DropVtable（每槽 24 字节）
    drop_fn_ : 单态化析构入口         ← 类型常量（同 T 全同）
    data_    : 数据区起址             ← 类型常量（= 块首 + 偏移，同 T 全同）
    meta_    : ?Sized 的类型元数据    ← 除切片长度外是类型常量
```

实测：`WeakChunk<()>` = **56 字节**，其中 `DropVtable` 占 **24 字节（43%）**。
而 N 个同类型对象就带 N 份完全相同的登记——**这是纯粹的重复**。

## 4. 设计方案：两级结构

核心判断：`drop_fn` / `data_offset` / `meta` 这三项都是**类型常量**，与具体对象无关，
因此应当"每个具体 `T` 只留一份"；槽位只需要一个键。

```text
第一级（每槽，1 个指针）
    weak 槽位 → type_record_ : NonNull<TypeRecord<T>>

第二级（每类型，1 份；与槽位无关，放在 Scope 的类型表里）
    TypeRecord<T> {
        drop_fn_     : unsafe fn(*mut u8, *const ())   // 单态化入口
        data_offset_ : usize                            // 块首 → 数据区
        meta_        : *const ()                        // ?Sized 的类型元数据（dyn 的虚表）
    }
```

取信息只需两级间接：`块首 →（偏移）数据区 → 由弱槽位取类型记录 → 调 drop_fn`。

### 4.1 为什么不需要"再找类型"

类型表按**类型**分表，而表项本身就是"同类型只此一份"的：构造记录时用
`drop_entry_::<T>()`（单态化函数的地址）做去重键。同一个 `T` 在任何调用点都得到同一个地址
（每个单态化一份，链接期常量），因此：

- 不需要 `TypeId`，不依赖 `'static`，`no_std` 下同样可用；
- 不需要哈希与字符串，键就是已有函数的地址；
- 若类型不需要析构（`needs_drop::<T>() == false`），记录里 `drop_fn_` 为空，连表项都不必建。

### 4.2 为什么"计算地址很复杂"不是问题

`data_offset` 在**构造记录时算一次**，此后是常量读取。它本来也不需要每次现算——
现在的代码正是因为每槽存一份 `data_` 才显得"简单"，代价是每对象 8 字节的重复。

`?Sized` 时偏移 = `size_of::<StrongChunkBase>()` 向上取整到 `align_of::<T>()`；要让它对所有
`T` 都等于同一个常数，可以给数据区加一条统一对齐约束（在 `data_` 前插一个 8 字节对齐的
零大小字段，`Sized` 的 `T` 天然满足）。这条约束与否是本方案唯一需要权衡的取舍点：
不接受约束时，偏移就按类型的 `align_of` 记录在记录里，同样成立，只是不能省掉读取。

### 4.3 切片长度的例外

`meta_` 里 `dyn Trait` 的虚表是类型常量，可入类型表；但 `&[T]` 的**长度是逐对象的**，
不能进表。切片这一支有两条出路：

- 弱槽位保留一个字存长度（`?Sized` 的切片类型才付这个代价）；
- 或由强块的 `cell_len_`（本块占用的 cell 数）推算——它与长度成比例，本来就是每块一份。

若走后者，槽位可以完全不保留任何逐对象元数据。

### 4.4 类型表放哪里

放在 `RootScope` 上（该 Scope 树共用一张），理由：

- 池与槽位本来就属于某个 Scope 树，类型表与它们同生命周期，随 root 回收即可；
- 不需要全局锁，也就不会引入跨 root 的同步；
- 唯一需要处理的是并发建表：多个线程首次分配同一个 `T` 时要去重，可以用 CAS 插入 +
  比较 `drop_fn` 地址实现；表项一旦建立就不再变化，读路径无锁。

## 5. 为什么这个方案能够成立

1. **三项信息确实是类型常量。** `drop_fn` 由 `T` 决定；`data_offset` 由 `StrongChunk` 的布局
   与 `align_of::<T>()` 决定；`meta` 除切片长度外由 `T` 决定。三者都与"是第几个对象"无关，
   因此把 N 份折成 1 份不丢信息。
2. **槽位本身不引入新的构造负担。** 记录是"每个具体 `T` 首次分配时建一次"，不是每次分配
   都建；分配路径只是把记录指针写进槽位，与现在写三个字段相比更简单。
3. **对 `?Sized` 仍然可行。** 重建胖指针需要的元数据（虚表）在记录里，切片长度用 §4.3 的
   出路之一解决。我们已经在 `WeakChunk` 这一侧验证过"元数据可以长期保存并原样复原"
   （见 `weak_chunk_rebuilds_unsized_data_from_metadata` 测试）。
4. **不影响"恰好析构一次"。** 判据仍然是 `DataState` 上的认领 CAS，与记录放在哪里无关；
   记录只回答"怎么析构"，不回答"该不该析构"。
5. **与调研结果不冲突。** 现成实现不需要这张表，是因为它们要么同构、要么让句柄承载类型；
   sw-scope 的兜底路径两者都没有，所以显式记录是必要代价，而按类型去重是把这份代价压到
   最小——本质上是**把同构 arena 免费得到的东西，在异构 arena 里用一次查表换回来**。

## 6. 收益与代价

| 项 | 现状 | 方案 |
| --- | --- | --- |
| 每槽类型信息 | 24 字节（3 字） | 1 个指针（或 u16 下标 + 对齐约束可更小） |
| 每类型额外开销 | 0 | 1 份记录（约 3 字）+ 表项 |
| 同类型 N 个对象 | 24N 字节 | 约 8N 字节 + 常数 |
| 取析构信息 | 直接读 | 一次指针跳转 |
| 新增机制 | 无 | 按类型登记表 + 并发去重 |

**待确认的取舍**：

1. 类型表挂 `RootScope`（随树回收、无全局锁）还是 crate 级静态表（跨 root 共享、需全局锁）？
   当前倾向 `RootScope`。
2. 是否接受"数据区统一 8 字节对齐"这条约束？接受则偏移是编译期常数，`?Sized` 与 `Sized`
   一视同仁；不接受则偏移记录在类型表里（仍成立，只是省不下那一次读取）。
3. 切片长度：留在弱槽位一个字，还是由 `cell_len_` 推算？


## 7. 为什么不能"到处直接 `drop_in_place`"（补充）

第 4 节的方案容易被误解成"为了省字节新造了一套机制"。事实相反：**能直接调用单态化
`drop_in_place` 的地方，本来就应该直接调用**，擦除登记只为"手里没有类型"的那一处存在。

按路径拆开看：

| 路径 | 编译期有 `T` 吗 | 能否直接 `drop_in_place` | 真正要做的事 |
| --- | --- | --- | --- |
| `Owning<'a, T>` 析构 | 有 | **能**（句柄单态化） | 认领状态 + 析构数据 |
| `Sharing<'a, T>` 计数减到 0 | 有 | **能** | 最后一次减计数者认领 + 析构 |
| `Retain<T>` 最后一个句柄 | 有 | **能** | 弱计数归零后的收尾（视策略定） |
| **清盘 sweep** | **没有**（只有 `WeakChunk<()>`） | **不能** | 只能靠登记的擦除入口 |

三点必须澄清：

1. **前三条路径的难点不是函数调用，而是认领。** 交接点必须把 `DataState` 从
   `Owning` / `Sharing` 推到 `Destroying → Destroyed`，否则 sweep 分不清"已被智能指针
   Drop 过"与"还欠一次析构"，就会重复析构。所以 `Owning` 必须写自定义 `Drop`
   （不能靠 drop glue 顺手跑数据区析构）——**这与是否保留擦除登记无关**。
2. **第四条路径不可省。** §8 给出具体会泄漏的写法。
3. **擦除登记已经是类型擦除的最小代价**：一个函数指针（把 `drop_in_place::<T>` 的地址带
   过去）+ 数据区偏移 + `?Sized` 的元数据。对 `!needs_drop::<T>()` 的类型，连记录都不必建。

第 4 节方案没有新增机制，只是把这三个**类型常量**从"每槽一份"改成"每类型一份"。

### 7.1 一条替代路线（供对比，未必采纳）

`bumpalo::boxed::Box` 之所以完全不需要这类登记，是因为它的析构**永远**发生在句柄 Drop
时、从不兜底。若 sw-scope 也改成"**`Retain` 自己就是析构责任人**"——最后一个 `Retain`
消失时无条件析构数据——那么"无人认领的对象"这个类别会消失，按类型的擦除登记也可省掉。

代价与限制：

- 弱槽位的回收无法再早于数据析构，`Retain` 的生命周期与数据强绑定；
- **仍然省不掉擦除调用本身**，只是把"按类型去重的一份"变成"跟着槽位走的一份"；
- 与 §8 的几种写法相比，兜底语义从"清盘负责"变成"最后一个句柄负责"，后者在"句柄被
  `mem::forget` / 泄漏"时同样无处兜底。

## 8. 什么情况下会泄漏（"从不兜底"语义的代价）

这一节回答：如果 sw-scope 也走 `bumpalo::Bump` 那条"清盘时不替对象负责"的路，
以及如果走 §7.1 那条"最后一个 `Retain` 负责"的路，分别在哪些**普通写法**下会泄漏。
§8.6 给出可运行的实证。

判断标准只有一条：**数据被析构，是否依赖于"某个人恰好还拿着句柄"**。只要依赖它，
那么"没有人拿着句柄"的每一种情形都会漏。

### 8.1 最要命的一种：句柄本身就是临时值

```rust
fn push_default(scope: &mut Scope) {
    // 只想把数据放进 arena，不需要句柄，于是连名字都不给
    scope.put(|| Thing::with_heap_buffer());
    // 分号让返回的 Retain 立刻被丢弃
}
```

`scope.put(...)` 返回 `Retain<Thing>`。这一行执行完，句柄当场析构，`Thing` 再没有任何
外部引用，但**数据区的析构还没有发生**：

- 若清盘兜底 sweep 存在：清盘时发现它处于 `Created`（还活着、无人认领），认领并析构。
  堆缓冲正常释放。
- 若清盘不负责析构（`bumpalo::Bump` 语义）：`Thing` 的 `Drop` 永远不会跑，
  `Thing` 里那个 `Vec<u8>` 的堆缓冲永久泄漏；`File`、`Mutex`、`Arc` 同理。
- 若改成"最后一个 `Retain` 负责"（§7.1）：这条恰好没问题，"最后一个句柄"就是刚刚析构
  的那个 `Retain`。但看下面几条。

### 8.2 `?` 提前返回：句柄在非预期路径上被丢弃

```rust
fn build(scope: &mut Scope) -> Result<(), MyErr> {
    let keep = scope.put(|| Thing::with_heap_buffer()); // 句柄
    let parsed: u32 = input.parse().map_err(|_| MyErr)?; // 提前 return
    // 想用 keep 做的事没做完，但 keep 在 return 时被析构
    Ok(())
}
```

`keep` 被析构时数据**没人认领**。清盘兜底在则无事；"从不兜底"则 `Thing` 泄漏；
"最后一个 `Retain` 负责"则没事。

### 8.3 panic 展开：同 8.2

```rust
fn build(scope: &mut Scope) {
    let keep = scope.put(|| Thing::with_heap_buffer());
    assert!(false); // 展开时 keep 被析构
}
```

展开会把局部变量逐个析构，所以"最后一个 `Retain` 负责"这一支也能覆盖；"从不兜底"则漏。

### 8.4 `mem::forget` / 故意泄漏句柄

```rust
let keep = scope.put(|| Thing::with_heap_buffer());
core::mem::forget(keep); // 句柄永远不会被析构
```

这条**任何"由句柄负责"的方案都救不了**（`forget` 之后没有责任人可执行）。只有"清盘兜底"
能救：sweep 看到该块仍处于活跃状态，直接认领并析构。这也正是为什么 §4 的方案里
清盘必须保留擦除析构的能力——它是最后一道、也是唯一一道不依赖句柄的防线。

### 8.5 `Sharing` 互相引用形成的环

```rust
struct Node {
    next: Option<Sharing<'static, Node>>, // 环：a.next = b, b.next = a
}
```

环内两个节点的强计数互相撑着，永远不为 0，所以**没有任何一次 `Sharing::drop` 会成为
"最后一次"**。结果：

- "由句柄负责"的两支都漏（没有句柄会触发析构）；
- 清盘兜底则能救：sweep 不管计数，只按"数据是否还活着"认领析构，环内每个节点各析构一次。

这与我们在 `strong-20260921-1935.md` §8 的结论一致：**不可达的环不会导致清盘漏 Drop，
但会推迟到清盘**——而"清盘必须能析构"正是这个推迟能成立的前提。

### 8.6 实证

上面的结论有一个可编译、可运行的对照实验：
[`sw-scope/drop-semantics-demo`](../drop-semantics-demo/README.md)。

它用 `bumpalo::Bump`（目前最常用的 Rust arena）复现 §8.1 / §8.4 / §8.5，并用进程级分配器
计数器 + 带 `Drop` 的探针类型给出两条独立证据。实测输出：

| 场景 | alloc | dealloc | 净泄漏 | drops |
| --- | --- | --- | --- | --- |
| 基线：普通作用域里的值 | 65536 | 65536 | 0 | 1 |
| §8.1 匿名临时值 | 66032 | 496 | **65536** | **0** |
| §8.4 引用丢失 | 66032 | 496 | **65536** | **0** |
| §8.5 互相引用的环 | 131568 | 496 | **131072** | **0** |
| 对照：`bumpalo::boxed::Box` | 66032 | 66032 | 0 | 1 |

（496B 是所有场景共同的 arena 自身 chunk 开销，与对象无关。）

对照组说明关键在于"谁负责析构"而不是 arena 实现：同一个 arena、同一份 payload，换成
由句柄负责析构的 `boxed::Box` 就净泄漏 0。

### 8.7 小结

| 写法 | `bumpalo::Bump` 语义 | 最后一个 `Retain` 负责 | 清盘兜底 sweep |
| --- | --- | --- | --- |
| 8.1 匿名临时句柄 | **泄漏** | 正常 | 正常 |
| 8.2 `?` 提前返回 | **泄漏** | 正常 | 正常 |
| 8.3 panic 展开 | **泄漏** | 正常 | 正常 |
| 8.4 `mem::forget` 句柄 | **泄漏** | **泄漏** | 正常 |
| 8.5 `Sharing` 环 | **泄漏** | **泄漏** | 正常 |

结论：**"清盘兜底"是唯一在五种写法下都不漏的那一支**，而它要求清盘流程能在不知道
`T` 的情况下析构——这正是 §4 那条擦除登记存在的全部理由。
